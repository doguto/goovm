# goosecc: design

goosecc is a C17 + GNU compiler written in Goose: preprocessor, parser and
type checker (milestone B1), and a lowering of the typed AST to GIR at -O0
that the Goose back-end (`backend-goose/`) compiles to an ELF object in the
same process (milestone B2). Since milestone D1 it also preprocesses and
parses C++17 and compiles a first subset of it (section 13). The front end follows clang-20 closely enough
that three oracles can hold it to clang on every corpus file (README.md,
"Results"):

- `goosecc -E` produces the same token stream as `clang-20 -E`;
- `goosecc --layout-check` emits `_Static_assert`s on goosecc's sizes,
  alignments, member offsets and declared types, which clang-20 must accept;
- `goosecc --dump-ast` prints the expression trees in clang's terms, and
  `tests/cmp_ast.py` compares them node by node (kinds, types, implicit
  casts and their cast kinds) with `clang-20 -Xclang -ast-dump=json`.

The lowering is held to clang by running the programs: every test of the
corpora is compiled by goosecc, linked with clang-20 and run
(`tests/suite_goosecc.py`).

This page covers the structure (1), the data (2), the preprocessor (3), the
parser and semantic analysis (4), how the code fits Goose's recursion rule
(5), the AST contract (6), the lowering to GIR (7), what is not
supported (8), what B3 did for speed (9), B4's persistent header
cache (10), B5's debug information (11), G1's start-up, parse cache
and clang-style folding (12), and D1's C++ front end (13).

## 1. Structure

One process, two passes. The preprocessor runs over the whole translation
unit first and appends every token to `tu_toks`; the parser then works on
that array with random access (it needs arbitrary lookahead only to tell a
cast from a parenthesized expression, a label from an expression, and so on).
With `-E` the tokens go to the printer instead.

## 2. Data

Everything that lives for the translation unit is a global growable array
(`T[>..]`); scratch buffers that are used as stacks are `T[>..<]`. Each global
is its own data stack (176 of them plus 6 runtime stacks with the lowering
and the back-end: `goose check --stacks`), so pushing to one never moves
another, and indices stay valid for the whole run. Nothing is freed. Each
region reserves 256 MB of address space (`build.sh`, section 9).

- **`src`**: one byte arena holding every file's text (each file once, with
  a NUL and a newline after it), the spellings of tokens built by `##` and
  stringizing, and cleaned copies of tokens that contain splices. A token's
  spelling is `(offset in src, length)`, and a **location** is an offset in
  `src`: `file_of` finds the file and `line_col` the line and column through
  the file's lazily built `line_starts`.
- **`names`**: a second arena for paths and option values.
- **Identifiers** are interned in an open-addressing table (a multiply
  hash over 8-byte words, computed by the same scan that finds the
  identifier's end; section 9). `Ident` holds the spelling, the
  current macro (or -1), the keyword and directive codes, flags.
- **`Tok`** is 16 bytes: kind, flags (start of line, leading space, no
  expand, from a system header, ...), `aux`, the spelling offset, `val` (the
  identifier id, or the spelling length), and `xloc`: the location of the
  token's outermost macro expansion, which `__LINE__` and diagnostics use.
- **Types** are uniqued in one table; a *qtype* is a `u32`, `(index << 4) |
  qualifiers` (const, volatile, restrict, _Atomic), so equal canonical types
  have equal indices and type comparison is an integer comparison. Typedef
  names are not types: a declaration's type is canonical. Function types keep
  their parameter list in `tparams`; records and enums refer to the `records`
  / `fields` / `enums` tables. Alignment overrides (`aligned`, `mode`,
  typedefs with `__attribute__((aligned))`) are separate type entries whose
  `canon` field points at the plain type. Qualifiers on an array type are
  pushed down to the element type, as clang canonicalizes them.
- **AST nodes** are 32 bytes (`kind, op, flags, ty, a, b, c, loc, v`) in one
  array; children are node indices and lists are runs in `nlist`, built in
  `nscratch` and committed when complete.
- **Symbols** (`syms`) are per declaration of an entity: kind, storage class,
  flags, type, scope depth, the definition node. Scopes are a log of bound
  symbols with marks; `id_ord`, `id_tag` and `id_label` give, per identifier,
  the innermost binding in each name space, and a symbol remembers the binding
  it shadows (`prev`), so leaving a scope restores the previous bindings.

## 3. Preprocessor

The goal was clang's `-E` token stream, quirks included, so the
implementation follows clang's Preprocessor/TokenLexer model rather than the
text-book algorithm:

- **Contexts.** A stack of file contexts and token contexts (macro
  expansions, re-injected streams). A macro is disabled while its context is
  on the stack, and a context is popped only when a token is read past its
  end, so that `f(1)(2)`-style rescans and the hide-set behaviour match. An
  identifier naming a disabled macro is marked "no expand" for good.
- **Arguments** are collected into `argtoks` (each ended by an EOF token);
  pre-expansion is lazy, in body order, and cached per argument, while the
  macro is still enabled (clang's order). `__VA_ARGS__`, `__VA_OPT__`, GNU
  named variadic parameters (`args...`) and the GNU comma elision of
  `, ## __VA_ARGS__` (only when the variadic argument is left out, and not in
  strict C99 mode with fewer than two parameters) are as in clang.
- **`##`** pastes by re-lexing the two spellings (`paste_two`) and checks
  that one token results; `#` stringizes with clang's spacing rules.
- **Directives.** `#include` / `#include_next` / `#import` with the search
  list `-iquote`, `-I`, `-isystem`, the system directories, `-idirafter`
  (`"..."` first looks next to the including file); a path cache; `#pragma
  once`; include guards detected like clang's MultipleIncludeOpt (any non-null
  directive or token outside the guard invalidates it, and the guard counts
  only if the macro was not defined at the `#ifndef`). `#if` / `#elif`
  (`#elifdef`, ...) are evaluated in `intmax_t`/`uintmax_t` like clang's
  PPExpressions; skipped blocks are scanned for directives only. `#line`,
  `#error`, `#warning`, `#ident`, `_Pragma` (deferred while an argument is
  pre-expanded, as clang does). Pragmas are printed under clang's rules
  (`once`, `GCC system_header`, `push_macro`, ... are not; `message` is
  canonicalized; `omp` lines are macro-expanded). `#pragma pack`, `ms_struct`
  and `push/pop_macro` take effect: pack and ms_struct become annotation
  tokens that the parser turns into a table of (token index, value) changes.
- **Builtin macros**: `__FILE__`, `__LINE__`, `__COUNTER__`, `__DATE__`,
  `__TIME__` (from `SOURCE_DATE_EPOCH` when set), `__INCLUDE_LEVEL__`,
  `__BASE_FILE__`, `__FILE_NAME__`, `__TIMESTAMP__`, and the `__has_include`,
  `__has_include_next`, `__has_builtin`, `__has_constexpr_builtin`,
  `__has_attribute`, `__has_c_attribute`, `__has_declspec_attribute`,
  `__has_feature`, `__has_extension`, `__has_warning`, `__has_embed`,
  `__is_identifier` and `__is_target_*` operators (`__has_cpp_attribute` is
  not defined in C, as in clang).
- **Predefined macros** come from `tools/gen_predef.py`, which records the
  output of `clang-20 -dM -E -x c /dev/null` (gnu17, -O0); goosecc derives
  the other modes from it (`-std=c89/gnu89/c99/gnu99/c11/gnu11/c17`, `-O1`
  and up, `-Os`/`-Oz`, `-pthread`, `-funsigned-char`), and the generator
  checks each of those deltas against clang. The answers to every `__has_*`
  query are probed from clang over ~142,000 candidate names taken from
  libclang's strings.
- **The printer** writes a token with a space where the source had one or
  where the two spellings would otherwise lex as one token, and follows
  source lines with newlines and line markers like clang's
  PrintPreprocessedOutput. Only the token stream is required to match.

## 4. Parser and semantic analysis

The parser is recursive descent over `tu_toks`, and semantic analysis is
done as each node is built: every expression node gets its type and value
category when it is made, and every implicit conversion is inserted at once
as an explicit node, so there is no second pass. The parts:

- **Declarations.** Declaration specifiers (all C17 type specifiers, GNU
  `__int128`, `_Float16`, `__bf16`, `_Float128`/`__float128`, `_Complex`,
  `_Atomic`, `typeof`/`__typeof__`/`typeof_unqual`, `__auto_type`,
  `_Alignas`, storage classes, `inline`, `_Noreturn`, `__thread`/
  `_Thread_local`, `__extension__`), declarators with GNU attributes in all
  their positions, K&R definitions and implicit `int` (as clang: errors in
  C99 and later unless downgraded), tentative definitions, redeclarations
  with composite types, block-scope `extern`, implicit function declarations
  (clang's rules for library builtins), `_Static_assert`, and `asm` labels.
- **Attributes** that change the types or the layout are implemented
  (`packed`, `aligned`, `mode`, `vector_size`, `ext_vector_type`,
  `transparent_union`, `ms_struct`/`gcc_struct`); `noreturn`, `weak`,
  `gnu_inline`, `cleanup`, `used`, `always_inline`, `const`, `may_alias`
  and asm labels are recorded on the symbol; the others are parsed and
  ignored (B2 will need `section`, `alias` and `visibility` recorded too).
- **Types.** Integer promotions (bit-fields promote by width, through
  assignments and prefix increments as clang's `getSourceBitField`), the
  usual arithmetic conversions including complex and `__int128`,
  compatibility and composite types, enums (underlying type `unsigned int`
  unless an enumerator is negative, as clang does for C), VLAs (each VLA type
  owns its size expression), flexible array members, vectors (GNU
  `vector_size` and clang `ext_vector_type` with swizzles).
- **Record layout** is the SysV x86-64 one as clang's
  ItaniumRecordLayoutBuilder computes it: bit-field allocation units, zero-width
  bit-fields (which affect alignment even in packed records, while unnamed
  bit-fields do not), `packed` on records and members, `aligned` on records,
  members and typedefs, `#pragma pack` (it caps member alignment), and
  `ms_struct` layout (including for unions).
- **Constants.** `fold_int` / `fold_float` evaluate integer constant
  expressions and arithmetic constants on the tree (with C's truncating
  division and remainder, unsigned wrap-around and the widths of the types);
  `sizeof`, `_Alignof` and `offsetof` are folded when the type is not
  variably modified. Null pointer constants are recognized as clang does (an
  integer constant 0, or such a value cast to unqualified `void *`).
  Initializers of objects with static storage are checked to be arithmetic or
  address constants (`init.goose`, with clang's extensions such as reads of
  `const` variables and compound literals).
- **Initializers** are parsed into a syntactic tree first; a walk resolves
  designators (including GNU ranges and anonymous members) and brace elision
  into (subobject path, value) entries, a stable sort orders them, and a
  build step produces the dense semantic initializer (6.5).
- **Builtins.** The types of clang's typed builtins come from
  `builtins_gen.goose` (generated by `tools/gen_builtins.py`, which reads
  them back from clang's AST of a call to each). The ones clang checks by
  hand get their result type in `builtins.goose`: atomics and `__sync`,
  overflow checks, `__builtin_shufflevector`, `__builtin_convertvector`,
  `__builtin_bit_cast`, the floating-point classification builtins,
  `__builtin_choose_expr`, `__builtin_types_compatible_p`,
  `__builtin_constant_p`, `__builtin_classify_type`, `__builtin_offsetof`,
  `va_*`. Builtins whose types involve `FILE` are typed once a `FILE`
  typedef is visible, as in clang.
- **Diagnostics** are `file:line:col: error: message` (to stderr), with the
  clang-20 defaults: incompatible pointer types are warnings, while
  int-conversion, implicit function declarations, implicit int and
  return-type mismatches are errors unless `-Wno-...` downgrades them.
  Warnings are printed only with `-Wall`.

## 5. Recursion under Goose's rules

Goose requires every function that is part of a call cycle to be declared
`recursive fn`, and inside a cycle it forbids nonfixed values (growable
arrays, owned strings) that are live across a call back into the cycle
(spec §7.8). The parser and the preprocessor are deeply recursive (94
functions are `recursive fn`), so the code is written so that the cycles
only ever hold fixed-size locals:

- **All growable state is global.** Token buffers, node lists, the
  initializer entries, the frames of the initializer walk, the macro
  argument buffers, the string builders: every one is a global array. A
  function in a cycle may push to them freely.
- **Global arrays used as stacks** carry their discipline in the code: a
  function records `mark = buf.len`, pushes, and resizes back to the mark
  when it is done (`nscratch` + `commit_list` for node lists, `ctxs`, `xbuf`
  with the context's `xbase`, `argtoks`/`argidx`, `pre`/`precache`,
  `streams` with `sbase`, `ifr`/`ients`/`ipath` in `init.goose`). Nested
  uses see the same buffer above their caller's part.
- **Results are indices, not slices.** Functions return node, type, symbol
  and token indices; text is returned as offsets into `src` or `names`. The
  few helpers that build text (`tname` for diagnostics, the layout and dump
  writers) write into a dedicated global buffer and are not called from a
  cycle while a previous result is still in use (the aliasing checker,
  spec §5.1, enforces this).
- **Recursive algorithms over types** (`type_name`, `compatible`,
  `composite`, the layout of nested records) either recurse with fixed
  locals only, or were rewritten as loops (the type printer is iterative).

The cost of this style is the number of global arrays (one data stack
each); NOTES.md has the details.

## 6. The AST contract

The AST is meant to be lowered to -O0 IR without any further semantic
analysis: every conversion is explicit, every node has its type, value
categories are explicit, and the forms that clang represents specially are
normalized. `tests/cmp_ast.py` checks this against clang's AST on every
corpus file, so where this section is silent, the clang AST of the same
code is the reference (node for node, see `dump.goose` for the mapping).

### 6.1 Roots

`tu_node` is an `N_TU` whose list holds, in source order, `N_FUNCDEF` (a =
symbol, b = body, v/c = parameter symbols), `N_DECL` (a = symbol, b =
initializer or 0; also for function declarations), `N_TYPEDEF`, `N_TAGDEF`,
`N_STATICASSERT`. A file-scope object may be declared several times; its
symbol is shared and at most one `N_DECL` carries an initializer
(`SF_DEFINED`); `SF_TENTATIVE` marks tentative definitions without one.
`syms[s].def` is the `N_FUNCDEF` of a defined function. Storage classes are
`syms[s].sc`; `SF_FILESCOPE`, `SF_INLINE`, `SF_WEAK`, `SF_THREAD`,
`SF_NORETURN`, `SF_GNU_EXTERN_INLINE` and the attributes in `sym_attrs`
(asm label, alignment, cleanup, ...) give the rest of the linkage
information.

### 6.2 Types and values

- `nodes[n].ty` is a qtype. Every expression is an lvalue (`NF_LVALUE`) or an
  rvalue; rvalues have unqualified types, except that a conversion to a
  pointer target keeps the target's qualifiers where clang does
  (`T *const p = 0`) and `_Atomic` is kept where it matters (Atomics, below).
- **Loads are explicit**: an lvalue used as a value is wrapped in
  `N_ICAST(CK_LVAL2RVAL)`. Arrays decay with `CK_ARRAY2PTR`, functions with
  `CK_FUNC2PTR`. Nothing else reads memory implicitly.
- **Discarded values** (expression statements, the init and increment of
  `for`, the left operand of a comma) are still lvalue-converted, as in
  clang's AST, and clang's -O0 code does load them (`x;` is a load).
- `N_ICAST` (implicit) and `N_CAST` (written) carry clang's cast kinds:
  `LVAL2RVAL, ARRAY2PTR, FUNC2PTR, NULL2PTR, INTEGRAL, INT2BOOL, INT2FLOAT,
  FLOAT2INT, FLOAT2BOOL, FLOATCAST, PTR2INT, INT2PTR, PTR2BOOL, BITCAST,
  NOOP, TOVOID, TOUNION, REAL2COMPLEX, COMPLEX2REAL, COMPLEXCAST, VECSPLAT,
  ATOMIC`. The semantics are clang's: `INTEGRAL` truncates or extends by the
  source's signedness, `INT2BOOL`/`FLOAT2BOOL`/`PTR2BOOL` compare with zero,
  `NOOP` changes only qualifiers (or the enum/int spelling), `BITCAST` is
  pointer-to-pointer or between vectors of the same size,
  `COMPLEX2REAL` takes the real part, `TOUNION` builds a union from a member
  value (GNU cast to union and transparent-union arguments).
- **Atomics**: a load of an `_Atomic` lvalue is `LVAL2RVAL` to the `_Atomic`
  type followed by `ATOMIC` to the value type; a store converts with `ATOMIC`
  to the `_Atomic` type. Compound assignments and `++`/`--` on an `_Atomic`
  lvalue keep the lvalue's `_Atomic` type: lowering must make them atomic
  read-modify-writes.

### 6.3 Expressions

Builtins that clang folds (`__builtin_constant_p`, `__builtin_classify_type`,

resolved to the selected expression.

### 6.4 Statements

`N_COMPOUND` (v/c), `N_DECL` (block-scope objects, in order; static locals
have `sc == SC_STATIC` and a constant initializer; a VLA declaration
evaluates the size expressions of its type, which are the `n` field of each
`TY_VLA` type), `N_IF`, `N_WHILE`, `N_DO`, `N_FOR` (a = `N_EXPR`, an
`N_COMPOUND` of declarations, or 0; b = condition or 0; c = increment or 0; v
= body), `N_SWITCH` (a = the promoted condition, b = body, v/c = the
`N_CASE`/`N_DEFAULT` nodes in order), `N_CASE` (v = value, already converted
to the condition's type; c = node holding the upper bound of a GNU range;
a = the statement), `N_DEFAULT`, `N_LABEL` (a = label symbol, b = statement),
`N_GOTO`, `N_IGOTO` (a = pointer), `N_BREAK`, `N_CONTINUE`, `N_RETURN` (a =
value converted to the return type, or 0), `N_EXPR`, `N_NULL`, `N_ASM` (a =
template string; op bits 1 goto, 2 volatile, 4 inline, 8 file-scope asm; v/c
= `N_ASMOP` operands: op 1 output (b = lvalue), 2 input (b = the expression
as written: lowering applies the lvalue conversion unless the constraint
takes memory), 3 clobber, 4 label (a = label symbol); a = the constraint
string). Conditions of `if`, loops and `?:` are scalar rvalues; lowering
compares them with zero.

### 6.5 Initializers

The initializer of an object (the b of its `N_DECL`, or the a of an
`N_COMPLIT`) is either an expression converted to the object's type, or an
`N_INITLIST` whose type is the (unqualified) aggregate type:

- a struct has one child per member in declaration order, except unnamed
  bit-fields, which have none (as in clang); a union has one child, the
  initialized member, whose field index + 1 is the list's `a` (0: an empty
  union initializer);
- an array has one child per element up to the last one initialized, and
  `b` = a filler node (`N_ZEROINIT` of the element type) when the array is
  longer; an array of unknown size has been completed (the list's type is
  the complete array type, and so is the symbol's);
- a member or element that was not initialized is `N_ZEROINIT` (of its
  type); explicit empty braces give an empty `N_INITLIST` instead;
- a character array initialized by a string is the `N_STRING`, with the
  array's type (the string is truncated or zero-padded to it);
- designators, ranges and brace elision are resolved: lowering never sees
  them.

Static initializers have been checked to be constant (4); lowering evaluates
them (address constants are `&designator ± integer`, possibly behind casts).

### 6.6 Functions

`N_FUNCDEF`: the symbol's type is the function type; v/c are the parameter
symbols (`SK_VAR` with `SF_PARAM`). A K&R definition (`int f(a) short a;`)
has the prototype of the promoted parameter types (`int (int)`), as in clang,
while the parameter symbols keep their declared types: lowering receives the
promoted value and converts it to the declared type, as clang's codegen does.
`syms[s].flags & SF_KRDEF` marks a function whose latest declaration is such a
definition. Labels are symbols in the function's label scope.

## 7. Lowering to GIR (B2)

`goosecc -c` lowers the typed AST of section 6 to GIR version 2
([`../gir/README.md`](../gir/README.md)) and hands the tables to the Goose
back-end in the same process: `main.goose` imports `backend-goose` as a
package (`import cg from "../../backend-goose"`), and `gen::codegen()`
calls `gir_codegen` with slices of the lowering's global arrays and writes
the bytes it returns. There is no LLVM anywhere: one Goose program
preprocesses, parses, checks, lowers and generates machine code. The
semantics are clang-20's at -O0 (its CodeGen as the C++ exporter sees it in
LLVM IR), so `tools/goovm-llc/gir_export.cpp` is the reference for how each
construct is written in GIR.

The lowering lives in namespace `gen` (so that its names cannot collide
with the front end's or the back-end's), in these files:

| file | content |
|---|---|
| `gen_ir.goose` | the GIR tables, type interning, constants, instruction emission, blocks, the function layout (`fn_finish`) |
| `gen_abi.goose` | C types as GIR types; the SysV classification and clang's coerced types (`Abi` records) |
| `gen_ops.goose` | instruction helpers with constant folding, C scalar conversions, loads/stores, GEPs, block copies, library calls |
| `gen_expr.goose` | expressions: lvalues, scalars, complex values, aggregates, conditions, assignments, compound literals, statement expressions |
| `gen_call.goose` | calls, returns, `va_arg` |
| `gen_stmt.goose` | statements, local declarations and initializers, switch, labels and gotos, cleanups, function bodies |
| `gen_glob.goose` | linkage, deferred definitions, string literals, static initializers (bytes and data relocations), address constants |
| `gen_builtin.goose` | builtins, library builtins, overflow checks, FP classification, atomics |
| `gen_asm.goose` | inline assembly: operand binding and a small AT&T assembler |
| `gen_debug.goose` | `-g`: the debug tables (compile unit, subprograms, lexical blocks, locations) |
| `gen_tu.goose` | the driver, constructors/destructors, aliases, `--emit-gir` |

### 7.1 The builder

The module tables (`m_types`, `m_insts`, `m_consts`, `m_globals`, `m_data`,
...) are global grow-only arrays of the back-end's own record structs
(`backend-goose/gir.goose`), so handing them over costs nothing. Since
`gir_codegen` stores the slices in its global `M`, Goose's aliasing check
then forbids `resize`/`clear` on them anywhere in the program (NOTES.md):
the tables only ever grow (`data_grow` appends zero pages).

A function's instructions are emitted into `f_insts` with local indices,
its static allocas into `f_allocas` (a local ref `ATAG + k`), and blocks
are numbers handed out by `new_block` and placed when `start_block` starts
them. Because a block, once started, is filled until its terminator, every
block is a contiguous run of `f_insts`, in start order. `fn_finish` lays
the function out in one pass: the allocas first (the entry block), then
the instructions, rewriting the value and block fields of each by the
opcode's operand mask (`OPM`) and the positions in `m_opnds` recorded by
`op_ref` / `op_blk`. Nothing is sorted or searched; a forward branch is
just a block number that is resolved when the function is finished.

Code after a terminator (`return`, `break`, a noreturn call) has no
insertion point; a statement without a label in it is then skipped, as
clang skips it, and anything that still needs code there gets a block
without predecessors.

Operations on constants fold (integer arithmetic, compares, casts, f32/f64
arithmetic), as LLVM's IRBuilder folds them for clang, so `x = 2 + 3`
stores 5. FP constants are deduplicated, as the exporter does, because the
back-end pools them by index.

### 7.2 Values

As in clang's CodeGen, every object lives in memory: locals and
parameters get allocas (at the alignment clang gives them: 16 for arrays of
16 bytes or more), and expressions are lowered by kind of value:

- `ex_val` gives a scalar GIR value (integers, pointers, f16/f32/f64/f80,
  vectors); `_Bool` is `i1` as a value and a byte in memory;
- `ex_cplx` gives the two parts of a complex value;
- `ex_agg(n, dst)` evaluates a struct, union or array into `dst`;
- `ex_lv` gives an `LV`: an address, a bit-field (the record address and
  the field), volatility.

Loads are explicit in the AST (`CK_LVAL2RVAL`), so every load the program
does is one GIR `LOAD`. Bit-fields are read and written through the
smallest integer covering their bytes (an `i24` for a field spanning three
bytes), with shifts and masks, so an access never touches a byte the field
does not use (clang loads the whole storage unit of the bit-field run).
Conditions are branched on directly (`&&`, `||`, `!` and compares become
branches, constant conditions fold), as clang does for `if` and `?:`
(for loop conditions it computes the value first), and the values of
`&&`, `||` and `?:` are PHIs. Complex multiplication and division follow
clang: the inline formula with a NaN check and the `__mul?c3` call,
`__div?c3`. `_Float16` arithmetic is done in float through the
`__extendhfsf2` / `__truncsfhf2` helpers, `__int128` division and FP
conversions are the compiler-rt calls (`__divti3`, `__floattidf`, ...).
VLA sizes are evaluated where the declaration (or the parameter list, or
the `sizeof`) is, kept per VLA type, and a scope with a VLA saves and
restores the stack pointer (also on `break`, `continue` and a jump back
before the declaration).

### 7.3 The calling convention

`gen_abi.goose` ports clang's `X86_64ABIInfo`: `classify` merges the
classes of the fields of each eightbyte (bit-fields, unaligned members,
unions, arrays, complex, `long double`, vectors of every size), with the
post-merge rules, and `arg_abi` keeps the register budget across the
arguments (a struct that does not fit in the remaining registers goes in
memory, as a whole). The result is one `Abi` record per argument and
return:

| kind | GIR |
|---|---|
| direct | the value; `signed char`/`short` arguments and returns are `SEXT`ed to `i32` (clang's `signext`, which the exporter makes explicit) |
| coerced | one or two parts (`i8`..`i64`, `iN` for a 3-byte tail, `f32`/`f64`, a vector) loaded from the object at offsets 0 and 8; a two-part return is a GIR struct `{t0, t1}` |
| byval | a pointer to a copy, with the size and alignment in the ABI word |
| sret | a hidden first argument; the function returns it |
| ignore | empty structs |

The parts' types need not be clang's own (an SSE eightbyte holding two
floats is a `double` where clang writes `<2 x float>`): the registers they
occupy and the bytes they carry are the same. Calls of
unprototyped functions are variadic calls (`al` is set), as clang makes
them. `va_arg` is lowered inline as clang does it (register save area
with `gp_offset`/`fp_offset`, or the overflow area, PHI of the two
addresses). `tests/c` and a randomized cross test (`tests/abi_cross.py`:
struct, union, complex, `__int128`, `long double` and variadic
signatures; callee and caller compiled by clang and goosecc in all four
combinations) check it against clang-20.

### 7.4 Globals and data

An entity with linkage is one GIR global, found by its linkage name (the
asm label, else the identifier); static locals (`f.x`), compound literals
at file scope, string literals (`.L.str.N`, identical ones shared) and
local constant initializers (`__const.f.N`, copied with one `MEMCPY`) get
private globals. Definitions are emitted as clang emits them:

- external definitions always, in source order;
- `static` functions and variables, and inline functions that are
  emitted, when something emitted refers to them (clang's deferred
  declarations: an unused static inline function in a header costs
  nothing and references nothing);
- C99 inline definitions (every file-scope declaration `inline` and none
  `extern`) not at all, GNU `extern inline` not at all, except that
  `always_inline` ones are emitted as local functions (clang inlines them
  even at -O0);
- tentative definitions as zero-filled definitions, or common symbols
  with `-fcommon`; `extern` declarations only when referenced.

Attributes that change the object: `weak`, `alias`, `visibility`,
`section` (variables and functions), `aligned`, `used`,
`constructor`/`destructor` with priorities (`.init_array.NNNNN` arrays, as
the exporter builds them), `cleanup`, `nocommon`; thread-local variables
are `TLS` globals reached through `TLSADDR`. With `-fPIC`, definitions
are preemptible (no `LOCALREF`).

A static initializer is written into the global's bytes in `m_data` by
`sinit`, which walks the dense initializer of section 6.5: integers by
`fold_int` (128-bit ones by `fold_int128`), floating-point values exactly
in their type (`static_f80` folds in long double and rounds per
operation, through C helpers; literals are converted from their spelling
with `strtod`/`strtof`/`strtold`), bit-fields by bits, strings truncated
or padded, compound literals by their initializers, flexible array members
by extending the object. Address constants (`eval_addr`) are a global plus
an addend (`&a[3].f`, `"str" + 1`, a compound literal, a function), an
integer, or label addresses: `&&l` is a `BLOCK` relocation and `&&a - &&b`
a `BLOCKDIFF32` one, whose block numbers are rewritten when the function is
laid out (that is why static locals are defined where they are declared,
inside the function being lowered). The relocations of one global are
contiguous and sorted by offset.

### 7.5 Builtins

`gen_builtin.goose` follows CGBuiltin.cpp at -O0. Library functions that
clang lowers itself are lowered when they are called by their names too
(unless the declaration is `static`, has an asm label, or `-fno-builtin`
says otherwise): `memcpy`/`memset` (inline `MEMCPY`/`MEMSET` up to 256
bytes, else the call), `memmove`, `abs`/`labs`/`llabs`, `fabs`,
`copysign`, `floor` and the other `const` math functions (folded for
constant arguments, as LLVM folds them), `alloca`, and `strlen`, `strcmp`,
`strncmp`, `memcmp` of compile-time strings (clang's constant evaluator).
The `__builtin_` operations map to GIR: bit counting (`CTLZ`, `CTTZ`,
`CTPOP`, `BSWAP`, `BITREVERSE`, `FSHL`/`FSHR`), `*_overflow` (`OVF` when
the types agree, else exact arithmetic in a wider type and a range check,
`__muloti4` for 128-bit operands), FP classification (`ISFPCLASS`),
`__builtin_setjmp`/`longjmp` (`SJLJ_*`), `va_start`/`va_copy`,
`return_address`/`frame_address`, `trap`, `unreachable`, `expect`,
`object_size` (folded for a declared object plus a constant, as clang's
constant evaluator does; else -1/0), `shufflevector`, `convertvector`, the
`_chk` functions, the SSE builtins clang's headers leave as builtins
(`maxps`, `minps`, `movmskps`, `packssdw128` and the immediate shifts as the
GIR `X86` op; `shufps`/`shufpd` as `SHUFFLE`; `cmp*ps`/`cmp*pd` as `FCMP`,
`SEXT`, `BITCAST`, as clang emits them), and
every `__sync_*`, `__atomic_*` and `__c11_atomic_*` function (`LOAD`/`STORE`
with orderings, `ATOMICRMW`, `CMPXCHG`, `FENCE`; compare-exchange loops for
the rest). `_Atomic` objects are loaded and stored atomically, and their
compound assignments are read-modify-writes.

### 7.6 Inline assembly

An empty template only evaluates its operands (an output tied to an input
gets the input's value). Any other template is bound as the exporter binds
it: fixed-register constraints (`a`, `d`, `S`, `t`, `u`, ...) as given,
`r`/`q`/`g` from the caller-saved pool, `m` as `(%reg)`, constant `i` as an
immediate, tied inputs to their outputs, symbolic names; the operands are
substituted into the template (`%0`, `%[name]`, `%k1`, `%c2`, ...) and the
result is assembled by a small AT&T assembler in Goose, which knows the
instructions the corpora use (integer moves and ALU operations with
register, memory and immediate operands, shifts, `lea`, `bsr`, `mul`,
`bswap`, SSE scalar arithmetic, x87 `fsqrt`/`fpatan`/..., `rdtsc`,
`cpuid`, fences). The machine code and the bindings become a `GirAsm`
record, exactly what the exporter produces with LLVM's MC layer. A
template outside that subset is an error with the text that could not be
assembled. File-scope `asm` is not supported (the exporter rejects module
assembly too).

### 7.7 Debug locations

With `-g` the debug tables are filled as the exporter fills them from
clang's metadata: one compile unit (the main file and the compilation
directory), a subprogram per function (name, file, line), a lexical block
per nested compound statement (made the first time an instruction needs
it), and for every instruction a (line, column, scope).

The locations follow clang's CodeGen rules (`gen_debug.goose`):

- every statement except compound statements, labels and `case` labels
  sets a stop point at its first token (a declaration at its first
  token, the store of an initializer at the variable's name);
- every expression the lowering visits (`ex_val`, `ex_lv`, `ex_cplx`,
  `ex_agg`, `ex_bool`) sets the location to clang's `getExprLoc()` and
  restores the previous one when it is done, as `ApplyDebugLocation`
  does: an operation is at its operator, a member access at the member, a
  subscript at its base, a call at its first token, a load at what is
  loaded; what a statement emits after its operands (a store, a branch, a
  `ret`) is at the statement;
- after a compound statement the location is its `}` (cleanups and the
  branch out of it), loop back-edges are at the loop, the condition of an
  `if` branches at the condition, the branch out of an `else` arm has no
  location, the prologue has none;
- a location inside a macro expansion, its arguments included, is the
  outermost invocation's name (clang's expansion location; the
  preprocessor records the extent of each function-like invocation).

Comparing the locations with clang-20's (through `goovm-llc --dump-gir`
of `clang -g` bitcode, instructions aligned per function) gives the same
line for 99.3% of sqlite3.c's 98,000 instructions and the same line and
column for 98.6%; what differs comes from code shape (clang's single
return block, the value-context `&&` of loop conditions) and from
parentheses, which the AST does not keep. The back-end makes the line
table from these locations (since A3), and B5 adds the DIEs: variables,
types, scopes, labels (section 11). The code of a `-g` object is the
`-O0` object's, except for the slots that hold VLA sizes for the
debugger (`__vla_exprN`).

## 8. Not supported

(For C; what the C++ front end does not do is in section 13.)

- `_BitInt(N)` (a clang extension in C17; no corpus file uses it) and C23
  syntax beyond what clang accepts in C17 mode (`#embed`, `constexpr`,
  `typeof` is supported).
- Objective-C, Blocks (`^`), OpenMP and OpenCL semantics (pragmas are
  passed through), Microsoft extensions beyond `ms_struct`, `__declspec`.
- Targets other than x86-64 Linux; the predefined macros are clang-20's for
  `x86_64-pc-linux-gnu` (no `-m`/`-march` deltas: the AVX-512 unit tests that
  need them are skipped by the corpus definition).
- Warnings: only the diagnostics needed for clang's errors are implemented;
  the warnings goosecc prints (with `-Wall`) are a small subset of clang's.
- Long double constants are folded in double precision by the front end
  (array sizes, `#if`, `_Static_assert`); the lowering evaluates the static
  initializers of `long double` objects in long double (7.4).
- In the lowering: `__float128` values (GIR has no fp128 type; an error),
  file-scope `asm`, inline assembly outside the assembler's subset, the
  SSE/AVX builtins that clang's headers leave as builtins other than those
  listed in 7.5 (`__builtin_ia32_cmpltss` and the other scalar compares,
  most AVX ones: an error naming the builtin), `-O1` and higher (accepted,
  code is -O0's), `__builtin_dynamic_object_size` (folded like
  `__builtin_object_size`, never computed at run time).

### 9.1 The process

A one-line file took 2.7 ms at B2's end; it takes 1.3-1.4 ms now (tcc
1.5 ms), and CTMark's 284 files pay that start-up and exit once each.

- **Static tables.** The builtin types (1,431 names) and the seven
  `__has_*` tables were dictionaries filled at start-up from the
  generated text. `tools/gen_tables.py` now computes open-addressing
  tables over those texts (offsets and slots as `const` arrays, which
  Goose emits as static data), and `tbl_find` probes them with the
  identifier's own hash.
- **Regions.** Each global growable array is a region of reserved
  address space. `build.sh` reserves 256 MB per region instead of the
  default 2 GB (`--stack-reserve 256M`), so that the regions a run touches
  are closer together and share page-table pages (5% of a CTMark
  compile); a table of one translation unit may then hold 256 MB (the AST
  of sqlite3.c is 6.4 MB). The number of regions went from 227 to 182:
  scratch globals became locals, parallel arrays became arrays of
  structs (switch contexts, block layout, per-symbol lowering state),
  option strings moved into `names`, and the lowering's u32-keyed
  dictionaries share two tables (`gmap`, keyed by `table << 32 | key`,
  and the per-function `fmap`). Each region costs an `mmap`, an
  `mprotect` and an `madvise` at start-up (NOTES.md, section 10).
- **musl.** A static glibc executable spends 0.5-0.7 ms of every run in
  glibc's start-up, mostly `init_cacheinfo` probing the caches with
  `cpuid`, which traps to the hypervisor in a VM. `build.sh` links
  against musl when its static library is installed (`LIBC=glibc` for
  glibc): the same C code and the same outputs, 0.6 ms less per file
  (-8.5% on CTMark).
- **Files.** A header is read with `open`, `fstat`, one `read` of its
  size plus one byte straight into `src`, and `close` (`goosecc_read_file`),
  instead of os's 7 calls. An object replaces the old file (unlink,
  create) rather than truncating it: ext4 flushes a truncated file's
  blocks when it is closed, 0.2 ms per object. A directory that does not
  exist is remembered in the path cache, so its lookups are skipped; the
  path cache is keyed by the lookup buffer itself when the path needs no
  normalization.

### 9.2 The preprocessor

Preprocessing is two thirds of the in-process time over CTMark, because
every file reads the glibc headers again (850 ms of 1,335 ms; 72% of it in
system headers).

- **The driver's token loop** (`pp_fill`, main.goose) now does `pp_lex`'s
  work for the common tokens: from a file, it lexes identifiers (with an
  inlined probe of the identifier table) and one-character punctuators
  itself and hands everything else to `lex_file_token`; from a macro
  expansion it copies the run of tokens up to the next macro name or
  paste. Only the first token of a run can change the include-guard
  state, which it tracks in a local.
- **Keywords** get their kinds as tokens are added to `tu_toks`
  (`keywords_init` runs before preprocessing), and `#pragma pack` /
  `ms_struct` changes are recorded by token index at the same time, so the
  pass over all tokens before parsing (`prepare_tokens`) is gone.
- **Macro expansion.** A function-like macro whose body has no `#`, `##`
  or `__VA_OPT__` (`M_SIMPLE`, set by `#define`) is expanded by
  `expand_simple`, which substitutes pre-expanded arguments without the
  general path's checks; arguments are collected from token contexts
  through `ctx_next` and from files through `lex_file_token`, without
  `pp_lex`.
- **Scanning.** The lexer dispatches on a 256-entry class table. An
  identifier's end and its hash come from one C helper
  (`goosecc_ident_scan`): 16 bytes classified at a time with SSE2, and
  the hash computed over 8-byte words (`(h ^ w) * K`, then mixed so that
  every byte reaches the bits the table indexes with; `tools/gen_tables.py`
  computes the same for the static tables). The text of skipped groups
  and the rest of directive lines is searched 16 bytes at a time for the
  only characters that matter there (newline, `/`, quotes, backslash,
  NUL: `goosecc_skip_text`), and comments and line tables use std's
  `find_any` instead of the C library's `memchr`.

### 9.3 Parsing, lowering, memory

- **Integer literals.** The overflow check `v > (2^64 - 1 - d) / base`
  divided by a value Goose does not know as a constant, which it does
  through a magic number computed bit by bit before the loop (60
  iterations per literal; NOTES.md, section 10). `mul_add_overflows`
  checks with a multiplication: -1.5 ms of parsing on sqlite3.c.
- **The per-function map** of labels and `case` blocks is a dictionary
  whose `clear` walks its capacity; it is cleared only when it has
  entries.
- **Pages.** The tables that grow large (tokens, AST nodes, symbols, GIR
  instructions, the source text) commit their next 64 KB at once
  (`goosecc_prefault`: `MADV_POPULATE_WRITE`), half the cost per page of
  faulting them in one by one (0.68 against 1.2 µs in this VM, unmap
  included). The source text of a file larger than 8 KB is committed
  before it is read.

### 9.4 What did not help, and what was not done

- Inlining `ident_lookup` into the lexer, `-fno-asynchronous-unwind-tables`,
  and huge pages for the large tables (`MADV_HUGEPAGE` past their first
  megabyte: sqlite3.c's page faults went from 6,155 to 4,323, its time did
  not change) were measured and left out.
- The word-wise identifier hash executes about as many instructions as
  the byte loop for identifiers of 7 characters; it is faster because it
  has no per-byte multiply chain and no per-byte bounds check.
- **A persistent header cache** was designed here and not finished; B4
  built it (section 10).
- **Lowering each function right after it is parsed** would keep the
  AST in the cache (lowering is bound by cache misses on AST nodes on
  sqlite3.c, 120,000 of them in a 2 MB cache simulation), but the order of
  the globals, functions and constants in the object follows the
  whole-unit order of `lower_tu` (unconditional definitions first, then
  what they reference), which per-function lowering would change.

### 9.5 Where the time goes now

Over CTMark (`--time`, sum of the best of 3 per file): preprocessing
850 ms, parsing and type checking 244 ms, lowering 117 ms, the back-end
91 ms, writing 17 ms, and 400 ms outside the phases (process creation,
start-up and exit, 1.4 ms per file). sqlite3.c: preprocessing 14 ms,
parsing 11.5 ms, lowering 9 ms, the back-end 7 ms; about 20% of its run
is the kernel (page faults, with memory-cgroup accounting; the read of
the source). tcc stays ahead on sqlite3.c (36 ms): it never stores its
tokens or an AST, and generates code as it parses.

## 10. The header cache (B4)

Over CTMark, preprocessing was two thirds of `goosecc -c`'s time in the
process, because every file preprocesses the same glibc headers again.
B4 adds a persistent cache (`src/hcache.goose`, with C helpers for the
file system in `goosecc_rt.h`): the effect of preprocessing an
`#include` is recorded once and replayed by later compiles, which then
leave *exactly* the state preprocessing would have left: the same bytes
in every array the later phases read. Everything compiled from that
state (`-E` output, diagnostics, AST dump, layout check, objects with and
without `-g`) is then the same with the cache cold, warm or disabled.

### 10.1 The unit and its key

A **unit** is one `#include` / `#include_next` / `#import` directive:
the search for the file, the file, everything it includes (and their
`#define`s, `#pragma once`, ...), up to the end of the file, when the
included file's context is popped. It starts in `do_include` once the
header name is known (a computed include is expanded before), so the
search and the loading of the file are part of it.

Which directives are units (`hc_unit`): an include of a system header
(`<...>`) from one of the program's own files (one that is not a system
header), and, from the second compile of a translation unit on, the main
file's `"..."` includes. Includes inside system headers are part of the
unit around them. A project's headers seldom repeat their context from
one file to the next (what was included before them differs, and with
it what they observe; ClamAV's `others.h` met 43 contexts in 98 files),
so recording them pays only where the same file is compiled again: the
first compile of a translation unit leaves a marker file
(`<hash of the configuration and the main file's spelling>.t`), and its
presence makes the main file's quoted includes units too.
(`GOOSECC_CACHE_QUOTED=1` makes every `"..."` include of the program's
files a unit at every compile; the adversarial tests use it.)

The **key** of a unit (`hc_key`) is: the configuration, the directive
(include / include_next / import, quoted or angled, the spelling), and
what of the includer its search uses: the includer's directory for a
quoted include, its search-directory index for `#include_next`, and
whether the includer is a system header. The **configuration** holds
what preprocessing depends on besides the observations: the format
version and goosecc's build identity (`build.sh` passes a hash of the
generated C), `-E` or not, the language mode (`-std` and the flags
derived from it, trigraphs), the keyword table's options, and the
include search list. The predefined macros and `-D`/`-U`/`-include` are
not in it: a unit observes the macros it reads, so `-DNDEBUG` and
`#define NDEBUG` before an include share entries.

### 10.2 What a unit observes

While a unit is preprocessed, a **recording** notes each read of the
state the unit started in. The reads go through hooks (`hk_*`), placed
at every place the preprocessor reads such state; each is a test of the
global `rec_on` and costs nothing when nothing records.

| observation | recorded at | checked by a replay |
|---|---|---|
| a macro tested (`#ifdef`, `defined`, a guard, "is this a macro") | `hk_mtest` | defined, or not (any definition) |
| a macro read (expanded, its flags read, saved by `push_macro`) | `hk_mread` | undefined, or the same definition: flags, parameters, body tokens' kinds, flags and spellings (`def_words`) |
| an identifier `intern` found or created | `hk_exist`, `hk_look` | it exists / does not (`intern` appends its spelling to `src` only when it is new) |
| a path looked up and nothing found | `hk_path_hit`, `hk_path_miss` | still no file there |
| a path where a file was loaded | `hk_path_miss` | not in the path cache, a regular file with the same identity |
| a path where a file loaded before was found | `hk_path_hit` | the same file (identity), the same state: `#pragma once`, guard, system header, included before |
| `__COUNTER__`, `#pragma pack`/`ms_struct`, `__INCLUDE_LEVEL__`, `__BASE_FILE__` | `hk_counter`, `hk_pack`, `hk_depth`, `hk_basefile` | the same value before the unit |
| the deepest include it reached | `hk_push` | the same depth stays within 200 |

Only the *first* read of a thing in a unit is an observation, and only if
the unit has not written it before: what it reads after its own write
follows from its own processing. Per identifier, `itouch` holds the
serial of the innermost recording that has tested (`m`), read the
definition of (`d`), looked up (`l`) and written (`w`) it; recordings get
increasing serials, and a recording with a serial at most the value has
seen the identifier. The recordings that have seen it are always an
outer part of the stack (seeing it in an inner one means seeing it in
all the outer ones; a new recording has seen nothing), so the hooks
compare one number and, on a first read, add an event for each inner
recording that has not. Files have the same serials (`rt`, `rw` in
`FileRec`).

A unit is not recorded (`hc_bad`) when it prints a diagnostic, expands
`__DATE__`/`__TIME__`/`__TIMESTAMP__`, pops a macro pushed before it,
reads a file whose stat cannot be trusted (10.5), or nests deeper than
60 recordings. Units with less than 2 KB of text and 64 tokens are not
worth a file.

**File identity.** A file is identified by its stat: device, inode,
size, modification and change times in nanoseconds (`goosecc_read_file`
keeps the `fstat` it does anyway). A change of contents changes the
change time (`ctime`), which no system call can set back (`touch -d`
sets `mtime`, and `ctime` to now). Timestamps are coarse on some file
systems, so a file changed twice within one tick could keep its stat:
a file whose `mtime` or `ctime` is less than 2 s older than the start of
the compile is "racy" and makes the unit unrecordable (and a file the
replaying compile itself read racily cannot stand in for an observed
one). This is git's index rule.

**Paths with no file.** A unit's search misses many paths (each system
header is looked for in every directory before its own: 400 such
observations in ClamAV's `others.h`). Each records, besides the path, a
**witness**: the deepest existing ancestor directory and its stat
(adding, removing or renaming an entry changes a directory's `ctime`),
when `lookup_file` saw that there was no such path or a directory there
(`goosecc_read_file` reports why it failed). A replay checks each
witness once (`wits` caches stats per process) and stats the path itself
only when its witness changed (a new file elsewhere in the same
directory, say). The path cache's answers count as the file system's.

**The path cache is a memo.** B4 moved its keys into their own arena
(`pnames`; a loaded file's normalized path is still copied to `names`),
so nothing outside the path cache depends on its contents or order: a
replay need not reproduce it, only keep it true. It adds the paths where
it loaded files (which must not be loaded twice) and leaves out the
paths with no file (a later lookup asks the file system).

### 10.3 Nesting

Recordings nest: each unit inside a recorded unit is recorded too
(`recs` is a stack), and an event goes to every recording it concerns
(`ev`, tagged with the recording's depth; a recording's events are
taken out when it ends). A replay inside a recording reports to the
recordings around it what preprocessing the include would have: the
identifiers it looks up (in order), the macros and files it observes
(as they are before it), what it writes. So a project header recorded in
a new context contains the replay of `<stdio.h>` inside it as if
`<stdio.h>` had been preprocessed.

### 10.4 The effect and its replay

At a unit's end (`hc_unit_end`, before `-E`'s line marker back in the
includer) the recording becomes a **variant** of its key: a head (the
observations above, checked before anything else) in the key's
manifest, and a blob (the effect) of its own:

- every array's suffix since the unit began: the text appended to `src`
  (the files' text, spellings made by `##`, `#`, `_Pragma`, splices),
  `names`, the files loaded (`FileRec`s), the macros defined and their
  tokens, the translation unit's tokens (or `-E`'s output, after the
  file's line marker), `-g`'s macro expansion ranges, the `#pragma
  pack`/`ms_struct` changes;
- the macros of identifiers it changed (undefined, one of its own, or by
  `pop_macro` the one it observed), identifiers it poisoned, the state of
  files loaded before it that it changed, `__COUNTER__` and the pack
  state after it;
- a table of the identifiers it refers to, in the order of their first
  lookup in the unit, with that lookup's offset.

**Relocation.** A replay appends each array's suffix at that array's
current end, so the blob's references are relative: an offset into the
unit's own text is relative to where `src` ended when the unit began;
macros, macro tokens, files and translation-unit tokens likewise.
Identifiers are the blob's local indices: the replay finds each by its
spelling, and creates the missing ones *in the table's order*, each
spelled at the offset of its first lookup. Normal preprocessing would
create exactly those identifiers (the ones that do not exist), in that
order (the order in which the unit first looks them up does not depend
on what existed before), at those offsets; so the identifier table, the
hash table aside, is the same.

**Anchors.** Some offsets point into text from before the unit: the
spellings of the tokens of a macro it observed (expanding `__THROW`
copies tokens spelled in `sys/cdefs.h`, loaded by an earlier unit), or
the text of a file loaded before and entered again (`stddef.h` with
other `__need_*` macros). Those are anchors: the candidates (token k of
observed definition j, its spelling or expansion location; byte n of an
observed file) are recorded, and the replay computes each candidate in
its own state and requires them all to agree. (A definition's tokens
are compared by spelling, not location, so the same anchor gives a
different offset in another translation unit: the one normal
preprocessing would copy.) Because tokens refer to observed macros only
through anchors, the effect of `#define LIMIT 7` and of `#define LIMIT
99` before the same header is the same blob, with two heads.

**Order of a replay** (`blob_replay`): check the head; map the blob;
verify its checksum; probe the identifiers and resolve the anchors;
append the arrays (taken back if a structural check fails, which a
correct checksum leaves to a bug); then what cannot be taken back: the
identifiers, the path cache, the changes to identifiers and files, `-E`'s
line marker and output; and end as `end_of_file` ends an include
(`back_in_includer`). The token arrays are relocated by a C loop
(`goosecc_reloc_toks`) that writes `Tok` records straight into the
arrays (the layout is checked by a static assertion).

### 10.5 Exactness

The preprocessor is a deterministic function of its state, the options
and the file system. Split its state into what the later phases read
(the arrays of 10.4, the macros, identifiers, files, counters) and the
rest: caches (line tables, the last file and line found, the identifier
hash table), the path cache (a memo of the file system), and scratch
(argument buffers, contexts: back to their old size when an include
ends). By induction over a unit's steps, if every first read of state
the unit did not write itself gives the recorded value (10.2), and the
file system answers as it did (identity, witnesses, or a new stat),
every step reads what it read when the unit was recorded and writes
what it wrote then, so the unit's effect is the recorded one; the
replay appends that effect relocated to where the arrays now end, which
is where the unit would have appended it. What the argument rests on,
and how it is checked:

- **every read of starting state has a hook.** The read sites of a
  macro (13 in `pp`, `ppdir`, `ppexpr`, `main`), of a file's state, of
  the path cache, the builtin macros with an outside value. Audited, and
  checked empirically: `--pp-state-hash=v` prints a checksum of every
  array the later phases read, and `tests/cache_check.py` requires the
  same checksum (and outputs) with the cache off, cold, warm and shared
  over the 2,357 corpus files.
- **file identity.** stat-based, with the 2 s rule above; a content
  hash would read every header at every replay.
- **checksums against corruption.** Every blob and manifest record
  carries a 64-bit checksum, verified before use; structural checks
  (every index in range) keep a damaged file that passes from crashing.
- **concurrency.** A blob is written to a temporary file and renamed; a
  manifest record is one `O_APPEND` write. A reader sees whole files or
  whole records (a torn trailing record ends its reading); concurrent
  writers can only duplicate a variant.

### 10.6 Files

The cache is `$GOOSECC_CACHE` (`off` disables it), else
`~/.cache/goosecc`, in a subdirectory `v1`; `-fno-header-cache` disables
it for one compile. All files are arrays of 32-bit words.

- `<key hash>.m`, a manifest: magic, version, the key, then one record
  per variant (magic, length, checksum, the blob's id and the head). A
  key that reaches 16 variants is volatile: its manifest is replaced by
  one holding a "volatile" record alone, the key is no longer looked up
  or recorded, and its includes are units of their own (ClamAV's
  `others.h`, 43 contexts in 98 files, had made every compile read a
  436 KB manifest only to find that out). Variants are tried newest
  first.
- `<key hash>-<blob id>.b`, a blob: magic, version, length, checksum,
  the key (checked against the lookup's), the identifier table, the
  anchors, the source text, the rest of the effect. The id is the
  blob's checksum, so equal effects share a file.
- `<hash>.t`: the translation-unit markers of 10.1.

`GOOSECC_CACHE_SIZE` (default 2 GB, with K/M/G) bounds the size: on one
new blob in 64 (on every one below 64 MB), the files are listed and the
least recently used deleted until the cache takes 3/4 of the limit (a
file's last use is the later of its modification and access times; a
manifest read or a blob mapped more than an hour after its last use has
both set to now, since access times alone are seldom kept: `relatime`
updates one once a day, `noatime` never); stale temporary files go too. A manifest whose blob was deleted
only misses: its include is preprocessed and recorded again. Files of another format version or build are never read
(their keys differ). `--cache-stats` prints the lookups, hits, misses,
recordings, bytes written, entries rejected as corrupt, and where a
replay's time went.

### 10.7 Speed

A replay costs about what copying its effect costs: the pages of the
arrays it fills (half its time; the same pages normal preprocessing
fills), checking the head (a stat of every file the unit loads, the
witnesses), the blob's checksum (read once from the page cache; the
later passes find it in the CPU's cache), probing and creating the
identifiers. On ClamAV's `table.c`, six replays take 0.8 ms where
preprocessing their headers took 2.0 ms; the main file's own text
remains. What helped, in order: mapping blobs instead of reading them
(no page fault per 4 KB of a fresh buffer), relocating tokens in C,
witnesses for the paths with no file (113 stats per unit to a handful),
comparing definitions as words against a per-process encoding of each
macro, verifying manifest records only when tried, and not adding the
paths with no file to the path cache. Recording costs 2-3 times a
preprocessing of the unit (the effect is serialized at every level of
nesting); appending manifest records instead of rewriting them, one
flat directory (`mkdir` and `ext4` inode allocation were a third of a
cold compile), and writing a blob in three pieces without assembling it
cut it by about a third. README.md has the measurements.

With one cache for a whole program, a key collects the variants of
many contexts and its manifest grows: a warm compile of a ClamAV file
reads 11 manifests, 620 KB, which with the head checks (210 stats) is
about a third of its replay time. Most of a head is spellings, mostly
the full paths its searches tried in vain (10 of the 16 KB of a
`sys/types.h` variant); storing them relative to their search
directories would shrink the manifests severalfold (not done). Volatile
keys had made it worse: every compile read `others.h`'s 436 KB to learn
that it was volatile, until such a key got a manifest of its own.

B4 also drops the Goose runtime's `madvise(MADV_NOHUGEPAGE)` per data
stack region at start-up, unless the kernel's transparent huge pages are
`always` (`build.sh`): under `madvise`, as here, it changes nothing and
costs a system call and a VMA split for each of the 314 regions, 0.27 ms
of every run (an empty file now compiles in 1.35 ms, as fast as tcc).

What was not done: caching the parser's state. After a replay, the
header's tokens are parsed again (about 0.5 ms of a typical CTMark
file); replaying declarations would need the same audit of the parser's
reads (scopes, typedef names, tags, redeclarations, the type table's
uniquing) that 10.2 does for the preprocessor, and its state is larger.

## 11. Debug information (B5)

With `-g`, goosecc emits the DWARF 5 that `clang-20 -O0 -g` emits for C:
the same DIE tree, with the same tags, attributes, forms and child order,
as `llvm-dwarfdump --debug-info` shows it (`tests/dwarf_diff.py`). What
is emitted:

- the **unit**: producer, `DW_AT_language` as clang picks it from `-std`
  (C89, C99, C11 for C11 and later), name, compilation directory, the
  string, address and line-table bases, and the code ranges;
- **global variables**, in the unit or (static locals) in their function,
  with `DW_OP_addrx` locations; the **string literals** a function uses,
  as unnamed variables (clang's `AddStringLiteralDebugInfo`); extern
  declarations get no DIE, as in clang; variable aliases become
  `DW_TAG_imported_declaration`s at the end of the unit;
- **subprograms** (code range, `DW_OP_reg6` frame base, prototyped,
  external, noreturn), **parameters** and **local variables** with frame
  locations, **lexical blocks** for the scopes clang opens (compound
  statements, an `if`'s condition, a `for`'s two scopes, statement
  expressions) when they hold a variable, **labels** with their address,
  and the artificial `__vla_exprN` variables that hold a VLA's element
  counts (an 8-byte slot stored after the allocation, as clang's
  `EmitAndRegisterVariableArrayDimensions`: the one change `-g` makes to
  the code);
- **types**: base types, pointers, `const`/`volatile`/`restrict`/`_Atomic`,
  typedefs (with `DW_AT_alignment` when aligned), arrays (subranges with a
  count, none for an incomplete array, a reference to the `__vla_exprN`
  variable for a VLA dimension), structures and unions (members with
  offsets, bit-fields with `DW_AT_bit_size` and `DW_AT_data_bit_offset`,
  alignments as clang computes them, unnamed members nested in their
  record), enumerations (underlying type, enumerators), subroutine types
  (unspecified parameters for `...`), GNU vectors (`DW_AT_byte_size` when
  padded), complex types; records, enums and typedefs declared in a
  function are children of its subprogram.

The tables are GIR's `dies` and `dattrs` (`gir/gir.h`), passed to the
back-end with `gir_codegen_ex`; the back-end resolves the GIR forms (code
ranges, frame offsets, strings, files) and drops the DIEs of scopes
without code (`backend-goose/DESIGN.md`, section 12). The back-end, GIR
and `tools/` are unchanged by B5. The builder, `src/gen_dwarf.goose`, is
a port of the part of `tools/goovm-llc/gir_dwarf.cpp` (itself a port of
LLVM 20's `DwarfDebug`/`DwarfUnit`) that runs for C at -O0 without
inlining, driven by a model of what clang's `CGDebugInfo` would have put
in the metadata. Without `-g` none of it runs, and the objects are
byte-identical to B4's except where `__PRETTY_FUNCTION__` is used (11.5).

### 11.1 Written types

The front end's types are canonical (section 2: a typedef name is not a
type), but DWARF names typedefs, from clang's sugared `QualType`s. With
`-g` the parser builds next to the canonical type of every declaration
its **written type** (`src/dtype.goose`), a 32-bit `dq`: bit 31 clear, a
canonical qtype (nothing in it was written with a typedef name); set, a
node of `dtypes` (a typedef name, or a pointer, array, VLA, function or
vector type over a written type) and qualifiers. Nodes are uniqued, as
clang's types are, so equal written types share one debug type. Side
tables hold the written type of each symbol, member, declaration (a
variable declared several times takes its definition's spelling), cast
and `__auto_type`; the function each block-scope record, enum and typedef
belongs to; the record an unnamed tag is nested in; the enumerators of
each enum and which integer constants name one; whether a function's
first declaration had a prototype (`DW_AT_prototyped` is the canonical
declaration's); the declaration lines of K&R parameters and `__label__`
labels. The rules are clang's: a typedef redeclaration is a new
declaration that later uses name; a parameter's written type is adjusted
(arrays and functions to pointers) with the element's spelling kept;
`vector_size` over a typedef makes a vector of the typedef; another
attribute that changes the canonical type drops the sugar.

### 11.2 Recording during the lowering

While a function is lowered, `gen_dwarf.goose` records its variables (the
symbol, its address as a GIR value, its scope record), labels and the
scope records of `gen_debug.goose` (one per scope clang would open, with
its parent, so variables can be put in the LexicalScopes tree later), and
a stream of **events** in lowering order: references to functions and
variables (`note_use`), string literals used as addresses, static local
definitions, explicit casts (clang's `EmitExplicitCastExprType` retains
the cast's type), enumerator references (clang's
`EmitDeclRefExprDbgValue` creates the enum's type) and local variable
declarations. A file-scope variable's initializer records events the same
way. Where clang visits less than goosecc lowers, the recording follows
clang's visits, not goosecc's code:

- a local aggregate with a constant initializer (clang's
  `IsConstantAggregate`, which accepts null pointers and static
  addresses) and a static initializer are emitted by `ConstExprEmitter`,
  which visits casts through initializer lists, compound literals and the
  casts it can emit (no-op, atomic, null to pointer, to union, integral)
  and no enumerator (`dbg_init_casts`, `dbg_no_enum`);
- the operand of a null pointer conversion is not visited;
- a condition of an `if` or `?:` that clang constant-folds
  (`ConstantFoldsToSimpleInteger` accepts `0 && x`, `1 || x`, the address
  of an object) and goosecc's lowering does not fold is lowered as
  before, but neither it nor the arm that cannot run records anything
  (`dbg_dead`), as clang emits neither;
- a `switch` whose condition clang folds emits only the statements that
  run, when clang's `FindCaseStatementsForValue` can collect them (from
  the case to a `break` at its level, nothing skipped that they may
  need): `sw_fold` is a port of it, and the condition, the case labels
  and the other statements record nothing;
- after an `if` whose arms both end in a jump, clang deletes the empty
  end block and has no insertion point, so it emits nothing up to the
  next label (`EmitStmt`); goosecc lowers those statements into a block
  without predecessors, quietly (`dbg_noins`);
- `int + pointer`, which the AST holds pointer first, records its
  operands' events in clang's (source) order;
- a function referenced through a declaration without prototype first
  gets a variadic `llvm::Function`, which its definition replaces at the
  end of the module (module order, 11.3); a reference after a K&R
  definition has a type without prototype (C99 DR 316) but its
  declaration's type has one, so it does not;
- the blocks the entry does not reach make no scopes and their labels are
  dropped (LLVM's `UnreachableBlockElim` runs at -O0).

### 11.3 Clang's order

The order of a unit's children is the order in which LLVM's `DwarfDebug`
meets them, which follows clang's `CodeGenModule`: global variables in
the order they were emitted, the enum types, the retained types (casts),
the functions in module order, the imported entities. `sim_run` replays
the recorded events in clang's emission order: external definitions
eagerly in source order, tentative definitions at the end of the unit
(the last one acts as the definition; a static one only if referenced),
and the deferred definitions (static functions and variables, inline
functions) depth-first as `EmitDeferred` emits them, each once code that
is emitted references it. A function's position in the module is its
first reference or its definition (`GetOrCreateLLVMFunction`), except
that a definition after references without prototype makes a new one at
the end. String literals, static locals and casts take their positions
from the replay too.

### 11.4 Types, scopes and DIEs

Types become metadata nodes (`md_of`) uniqued structurally, as LLVM
uniques metadata, so one DIE serves every equal type; DIEs are created
top-down as `DwarfUnit::getOrCreateTypeDIE` creates them (a pointer's DIE
before its pointee's), in the context clang gives them (the unit, a
subprogram, or the enclosing record of an unnamed member). Per function,
`function_dies` builds LLVM's LexicalScopes from the instructions' debug
locations (a scope per location's scope, enclosing scopes first, in
first-use order; `#line` file changes are transparent lexical block
files), puts the variables (the frame-indexed ones first, as LLVM's
`MachineFunction` table holds them: allocas and byval parameters;
parameters by argument number) and labels in their scopes, and flattens scopes without
variables, as `DwarfCompileUnit::createScopeChildrenDIE` does. Most
attribute values are added at the end, as LLVM's
`finishSubprogramDefinitions` and `finishEntityDefinitions` add them,
which is when most types are first referenced and so where their DIEs
go. Source locations are clang's presumed locations: `#line` changes the
file and line (`ppdir.goose` records each directive; a header-cache
recording that meets one is not stored), and a location inside a macro
expansion is the outermost expansion's.

### 11.5 `__PRETTY_FUNCTION__`

goosecc had made `__PRETTY_FUNCTION__` the function's name, like
`__func__`. Clang prints the function's type as written: `int f(int, char
**)`, `const char *g(void)`, `void h()` without a prototype, `int
(*k(void))[4]`, typedef names kept (`size_t`, `FILE *`). The string's
array type showed in the debug information of about 60 corpus files
(`assert` uses it), so B5 implements it (`pretty_function`, a port of
the C part of clang's `TypePrinter`). It needs the written types, so a
translation unit that uses `__PRETTY_FUNCTION__` builds them without
`-g` too (`pf_scan` looks for the keyword in the token array before
parsing); only the side tables are filled, and what `-g` changes in the
symbols stays behind `dbg_g`. Those files' objects without `-g` differ
from B4's in that string.

### 11.6 What differs from clang

B5 left 44 corpus files whose DWARF differs from clang's, all from code
that goosecc generated differently; G1 (section 12.3) made the code
generation follow clang's folding, NRVO and inlining of nodebug
`always_inline` functions, and 9 remain (README.md, "Results", G1):

- **`always_inline` functions with debug information** (8 torture tests):
  clang inlines them at -O0 and describes each expansion with a
  `DW_TAG_inlined_subroutine` under an abstract subprogram; goosecc emits
  them out of line and calls them;
- a VLA's location list (`920721-2.c`) as the back-end writes it;
- **locations**: a variable that clang returns in place (NRVO) has a
  location list in clang (`DW_OP_breg`), a frame location with
  `DW_OP_deref` in goosecc; realigned frames use `DW_OP_breg7` in clang
  (`tests/dwarf_diff.py` counts these as "identical but for frame-location
  forms" when nothing else differs);
- goosecc's own bug: an array of VLA rows (`char c[10][n]`) gets a 1-byte
  allocation (wrong code, which its DWARF follows).

## 12. Start-up, the parse cache and clang's folding (G1)

Milestone G1 made three changes: a process start-up well below a
millisecond (12.1), a second persistent cache that replays the parser's
state after a file's leading includes (12.2), and the code generation
that clang-20 does at -O0 beyond a plain translation (12.3); `noinit`
compiles (12.4). Results and measurements are in README.md ("Results",
G1).

### 12.1 Start-up

A compile of a one-line file took 1.19 ms of wall time, about half of it
the Goose runtime reserving goosecc's 420 data stacks (every growable
global array is a region of its own: an `mmap` of 257 MB, an `mprotect`
of its guard gap, two VMAs to unmap at exit). The runtime is embedded in
the generated C, so `build.sh` patches that copy
(`runtime-patches/lazy-regions.patch`; the patch, its measurements, its
risks and a proposal for the Goose authors are in
[runtime-patches/README.md](runtime-patches/README.md)):

- all of main's regions are slots of **one** `PROT_NONE` reservation
  made at start-up;
- a slot becomes accessible on its first access: the runtime's SIGSEGV
  handler `mprotect`s it and the access is retried; guard gaps stay
  inaccessible;
- the 146 regions nearly every compile touches (`hot-regions.txt`, made by
  `hot_regions.py` from a profiling build over CTMark) take the first
  slots, packed so that their first pages share page-table pages, and are
  enabled as they are reserved.

goosecc's own start-up work moved to where it is needed: `goosecc_commit`
(`goosecc_rt.h`) touches the top of a stack before a `read()` into it,
so that the kernel does not fault page by page inside the system call.
One-line file: 0.65 ms (0.63 ms task-clock, `exec` and exit included).

### 12.2 The parse cache

`src/pcache.goose`. With the header cache warm, preprocessing a CTMark
file costs little, and the parser's work on the same glibc declarations
(types, symbols, AST nodes for every prototype) became the largest
repeated cost. The parse cache saves the parser's state after the leading
includes and replays it.

**The prefix.** A translation unit nearly always begins with a run of
`#include` lines (directives between them, no token of the main file's
own): its prefix. Preprocessing makes the prefix's tokens `[0, t1)`
before parsing starts. `pt_inc_begin` / `pt_inc_end` (`ppdir.goose`)
follow the main file's top-level includes: each records its token, text
and identifier ranges and, when the header cache replayed or recorded it
as a unit, the blob id (`hc_top_bid`); the first token of the main file's
own ends the prefix.

**The key (chain).** The parser's state at `t1` is a function of the
tokens `[0, t1)`, of the text and identifiers they refer to, of the
options, and of the state it starts from. `types_init` and `parse_init`
now run before preprocessing so that the starting state is fixed. The
chain hashes the configuration, the options, goosecc's build id, the
built-in text, the identifiers that exist before the first include, and
per include its blob id (which determines its tokens and text) or a
checksum of its tokens and text, plus what the main file's directives
added between includes. Two compiles with the same chain have the same
tokens with the same identifier numbers; source offsets after the main
file's text are shifted by the difference of the main files' lengths.

**The entry** (`<cache>/<key>.p`) is the state at `t1` as a delta from the
starting state: for each of 29 tables (types, records, fields, symbols,
attributes, AST nodes and lists, strings, scopes, the debug-type side
tables, ...) the part appended since the start and the changed words of
the part that existed; the dictionaries, written whole; the scalars. Every
field that holds a source offset is relocated on replay (offsets in the
main file stay, offsets past it move by the length difference); per AST
node kind, the fields that are locations are known (`goosecc_pc_nodemask`:
`N_FLOAT.b`, `N_COMPOUND.b`, `N_DECL.c` besides `loc`). The parser may
lex builtin signatures while it parses the prefix (`builtin_type`); the
entry lists them and a replay lexes them again, in order, first.

**Exactness.** Not cached: a prefix with a diagnostic, one whose parse
looked past `t1` or did not end at file scope exactly at `t1`, one that
reaches into the main file's text (a macro the main file defined expanded
in a header), state that refers to identifiers or text the main file
added. `--pp-state-hash` includes a hash of every parser table, so
`cache_check.py` compares the whole parser state, not only the outputs;
`pcache_check.py` replays every corpus file's prefix into a compile whose
main file is padded (`GOOSECC_TEST_MAIN_PAD`), so that every offset moves.

### 12.3 What clang-20 folds at -O0

clang's CodeGen asks its constant evaluator in a few places, and what the
evaluator can read changes the code and the DWARF: `tryEmitAsConstant`
for a read of a variable, `VisitMemberExpr` for an integer member,
`ConstantFoldsToSimpleInteger` for the condition of an `if`, `?:`, `&&`,
`||` and loops, `EmitBuiltinExpr` for a builtin call, and Sema's array
bounds in GNU modes. goosecc's evaluator (`fold_int`, `fold_float`,
`fold_bool`, `fold_addr` in `sema.goose`) follows it when `fold_cvars` is
set, which the lowering does (the parser's integer constant expressions
never read variables):

- **const variables.** A non-volatile, non-weak `const` variable (or array
  of such) with a constant initializer is read from its initializer
  (`cvar_init`, filled by the parser), with members, elements, string
  elements, and through const pointers (`p->f`, `p[i]`, `*p`). The
  initializer must be one clang had seen when it emitted the code: an
  external definition is emitted as it is parsed, a deferred one after
  the unit (`cv_ctx`, `cv_ctx_late`). Integer, floating and pointer reads
  become constants; a file-scope variable that is internal and unused
  gets a DIE with `DW_AT_const_value` (or without location for a pointer)
  instead of being emitted (`EmitDeclRefExprDbgValue`, `EV_CVAL`).
- **addresses**: differences and comparisons of addresses of one object,
  an object's address against a null pointer (unless weak), `offsetof`
  written as `(size_t)&((T *)0)->m`.
- **`strlen` and `memchr`** (and `__builtin_` forms) of string literals,
  const character arrays and pointers to them (`cptr_eval`: the array's
  initializer, its length, the index; reading past the array fails, as in
  clang).
- `__builtin_huge_val`, `__builtin_inf`, comparisons of complex constants.
- **`__builtin_constant_p`** of an operand that does not fold while
  parsing (0 there, as in a constant context) is decided again in CodeGen
  (`NF_BCP`): it folds to 1 if the operand then folds, and otherwise is
  not folded at all, so a `?:` on it keeps both arms, as in clang.
- **GNU array bounds** that only the evaluator folds give constant-size
  arrays (`fold_gnu`).

Also:

- **NRVO.** clang applies the named return value optimization in C
  (Sema's `computeNRVO`, scope by scope: `nrvo_mark` in `gen_stmt.goose`
  replays `Scope::updateNRVOCandidate` / `applyNRVO`). With an `sret`
  return the variable lives in the caller's memory (no copy at the
  return; its location is the `sret` pointer's); with an ignored return
  (an empty struct) it has no debug information.
- **nodebug** functions have no subprogram, locations or variables;
  what clang's CodeGenModule records for them (retained cast types,
  string literals, references) stays (`dbg_nodebug`).
- **always_inline.** clang inlines `always_inline` functions even at -O0.
  goosecc expands calls of the `always_inline` + `nodebug` ones (the x86
  intrinsics headers) in place (`inline_call`, `gen_call.goose`): the
  arguments go to fresh parameter slots, the body is lowered into the
  caller with its returns storing the result and branching past it, and
  every instruction is at the call (LLVM's `fixupLineNumbers` for a
  callee without debug information). A function only ever expanded is not
  emitted; with `-g` it is still lowered once, its code dropped
  (`gen_function_dropped`), for what clang's emission of it records
  (`EV_REFSYM`). `always_inline` functions with debug information are
  still emitted out of line and called (clang inlines them and describes
  them with `DW_TAG_inlined_subroutine`s: README.md lists the files).
- `DW_AT_prototyped` of a function first declared at block scope without
  a prototype is that declaration's (clang's local extern declarations).

### 12.4 `noinit`

`__attribute__((noinit))` is ignored by clang-20 on x86-64 (a warning),
so goosecc ignores it too. Making it compile exposed two bugs in named
sections: a tentative definition in a named section got data instead of
zeros, and the first section name could land at string offset 0 (read as
"no section"). `tests/c/52_noinit_sections.c` covers both.

## 13. C++ (D1)

Milestone D1 is the first stage of a C++ front end in the same program:
`goosecc` compiles a file as C++ when its extension is `.cpp`, `.cc`,
`.cxx`, `.C`, `.c++`, `.cp` (or a header extension, or with `-x c++`). The C path is untouched by it: every C
output of every corpus file is byte for byte the one of the build before
D1 (`cmp_bins.py`, README "Results"). What D1 does:

- preprocessing identical to `clang++-20 -E` (13.2);
- parsing and declaration semantics of C++17 (C++98 to C++23 for what the
  headers use), with no false error on any corpus file and on the C++11-17
  libstdc++ headers (13.3 to 13.6);
- the Itanium record layout and name mangling, held to clang by two
  oracles (13.7, 13.8);
- code generation for "C with classes" through the C lowering (13.9).

### 13.1 Structure

The C++ front end is a second parser, `src/cx_*.goose` (namespace `cx`,
11,400 lines), next to the C parser, which it does not change. Both share
the token array, the type table, the symbols, the AST nodes and the C
semantic functions (`sema.goose`, `expr.goose`, `init.goose`); C++ adds
side tables indexed like the shared ones rather than new fields in them,
so that C's memory layout and speed stay as they were:

| file | what |
|---|---|
| `cx_core.goose` | C++ keywords, scopes (`scopes`, `nmap`), the per-symbol `cxs` table, the per-record `crecs`/`cbases` tables, templates (`tmpls`, `tparams`, argument lists), the new type kinds, lookup |
| `cx_names.goose` | the token cursor (`save`/`restore`, `>>` splitting), qualified names, template argument lists, operator names |
| `cx_decl.goose`, `cx_decl2.goose` | attributes, decl-specifiers, declarators, declarations, functions, variables, namespaces, using, linkage specifications, the translation unit |
| `cx_class.goose`, `cx_layout.goose` | classes, enums, member lists, deferred member bodies; the Itanium layout |
| `cx_tmpl.goose` | templates, specializations, substitution by re-parsing |
| `cx_expr.goose`, `cx_sema.goose`, `cx_over.goose`, `cx_stmt.goose` | expressions, their semantics, overload resolution and conversions, statements |
| `cx_mangle.goose`, `cx_check.goose` | Itanium mangling; the declaration dump and the layout oracle |
| `cx_gen.goose` | code generation (13.9) |

New type kinds (`types.goose`): `TY_LREF`, `TY_RREF`, `TY_MEMPTR`,
`TY_NULLPTR`, and the kinds of what D1 does not compute: `TY_TPARAM`,
`TY_DEPSPEC` (a template-id, with its argument list), `TY_DEPNAME`
(`typename Q::name`), `TY_DEPEXPR` (`decltype` of a dependent expression),
`TY_UNKNOWN`, `TY_AUTO`, `TY_PACKEXP`. New node kinds (`N_THIS` ...
`N_RANGEFOR`, 70-84) mark C++ expressions D1 parses but does not lower.

### 13.2 Preprocessing

The lexer gains `::`, `.*`, `->*`, `<=>` (C++20), the `<::` rule, raw
strings, user-defined literal suffixes, digit separators and the
alternative operator spellings (`and`, `bitor` ...). The predefined macros
are clang++-20's, per standard,
generated by `tools/gen_predef_cxx.py` from `clang++-20 -dM -E` as a base
set and per-standard deltas (`c++98`/`03`, `11`, `14`, `17`, `20`, `23`/`26`
and their `gnu++` forms) (`predef_cxx_gen.goose`), together with the
`__has_feature`/`__has_extension`/`__has_builtin`/`__has_cpp_attribute`
tables; `-fno-exceptions`, `-fno-rtti`, `-Wno-deprecated` and
`-fenable-matrix` change them as in clang. The include path puts
libstdc++ 13's directories before clang's resource directory. The header
cache keys include the language, the standard and these options.

### 13.3 Scopes and lookup

Every namespace, class, enum and block scope that C++ lookup needs is a
`Scope` (kind, parent, the symbol, the record). Names declared in a
namespace or class go into one dictionary, `nmap`, keyed by
`scope << 32 | identifier`, whose value is the newest symbol; older
declarations of the name in that scope are chained through `cxs[s].nnext`
(overload sets, redeclarations). Block scopes reuse C's `id_bind` binding
stack, so a local declaration costs what it costs in C. Lookup
(`cx_core.goose`) is C++'s: unqualified lookup walks the blocks, then the
scope chain (class scopes through their bases, namespaces through
using-directives and inline namespaces); qualified lookup searches the
nominated scope only. Templates use two-phase lookup: when a template's
tokens are parsed again for a substitution (13.4), namespace members
declared after the template are invisible (`vis_limit`, a token position),
while the substitution's own bindings (block-scope bindings) always are.

### 13.4 Templates

D1 stores a template as the token range of its declaration and the
records of its parameters (`Tmpl`, `TParam`). Uses of a template produce
`TY_DEPSPEC` types that carry the template and the (canonical) argument
list; two uses with the same arguments are the same type. D1 does not
instantiate class templates or deduce function template arguments (D2);
what it does compute:

- **alias templates and default template arguments**: the tokens are
  parsed again with the parameters bound to the arguments
  (`subst_parse`), which yields the aliased type (`std::enable_if_t`,
  `std::remove_cv_t` ...) and completes argument lists, so that mangled
  names carry the defaulted arguments as clang's do;
- **explicit specializations** are ordinary classes, found by their
  completed arguments (`spec_map`); partial specializations are matched
  when their arguments are those of the use;
- **dependent names** (`typename T::type`, `decltype(e)` of a dependent
  `e`) are opaque types.

Parsing a template's tokens again needs no copy of anything: the parser
state is the token position plus a few globals (`save`/`restore`), and
every growable buffer is a global stack (13.6).

### 13.5 Lenient semantics: no false errors

C++ cannot be checked completely without instantiation, so D1 checks what
it can compute and accepts the rest: an expression whose type depends on
something D1 does not compute is an opaque node (`N_CXX` with `NF_DEP`, or
`TY_UNKNOWN`), and every check passes on opaque operands. The C semantic
functions are called for expressions whose operands are C types (`cish`),
so C's diagnostics apply to C++'s C subset. Checked: declarations and
redeclarations, lookup (undeclared names outside templates), class
completeness, layout, constant expressions D1 evaluates (array bounds,
enumerators, `static_assert`, `sizeof`/`alignof`, type traits it
implements), overload resolution among non-template candidates, C's
checks on C operands. Not checked: anything inside templates beyond the
syntax, access control, `constexpr` evaluation of function calls,
narrowing, concepts and `requires` (C++20, the 75 header files of the
cxx-hdrs corpus that D1 rejects), exception specifications, most of
[over.ics] for user-defined conversions.

### 13.6 Recursion under Goose's rules, again

A C++ parser is more recursive than a C one: a declaration contains an
expression, which contains a lambda, which contains statements and
declarations; a template-id's argument is a type-id or an expression; a
substitution parses a template inside the parse of its use. The C++ files
have 195 `recursive fn`. Section 5's rules carry over unchanged, and
three more patterns appeared:

- **Re-parsing instead of copying.** Substitution, default arguments,
  default member initializers and deferred member bodies all move the
  token cursor to stored tokens and back; the state they need is a fixed
  `Save` value on the stack. No AST is ever cloned.
- **Scratch stacks per construct.** Class bodies push members, bases and
  member functions to `cfscratch`/`cbscratch`/`cmscratch` with marks (a
  local class inside a member function body nests above its enclosing
  class's part); code generation has `stmt_buf`, `abi_scratch` and
  `slot_scratch`.
- **Types written in prefix form.** The layout oracle's type names
  (13.7) would naturally be built inside out (a C declarator); building a
  string while recursing would keep a growable local alive across the
  recursive call, which Goose forbids. They are written left to right
  through helper class templates of the check file instead
  (`__gt_ptr< int >::t` is `int *`), a single append-only pass.

### 13.7 Records and layout

`cx_layout.goose` lays classes out as Itanium's C++ ABI does: the vtable
pointer of a dynamic class, the primary base (the first non-virtual
dynamic base), non-virtual bases in order, empty base optimization with
the map of empty subobjects at each offset, tail padding reuse except for
C++03 POD classes, bit-fields with C's rules, virtual bases after the
non-virtual part. `goosecc --layout-check` in C++ mode writes, for every
class it can name, `static_assert`s on `sizeof`, `alignof`, the offsets of
fields (and of the first field of each base), `__is_polymorphic`,
`__is_empty`, and the declared types of members and namespace-scope
variables; `tests/layout_check.py` compiles them with `clang++-20` (with
`-fno-access-control`). The assertions are C++98, so that the same file
checks every standard the corpus uses.

### 13.8 Mangling and the declaration oracle

`cx_mangle.goose` writes Itanium names: nested names, substitutions
(`S_`, `S0_`, `St`, `Sa`, `Sb`, `Si`, `So`, `Sd`), template
arguments, cv- and ref-qualifiers of member functions, operator and
conversion names, local entities of internal linkage (`L`), and ABI tags
(`[abi:cxx11]` of libstdc++'s inline namespace, with the implicit tags of
return and variable types). `goosecc --dump-decls` prints every
function and variable declared in the main file with its mangled name and
type; `tests/cmp_decls_cxx.py` compares them with clang's
(`tests/cxx_decls.c`, a libclang program printing `clang_Cursor_getMangling`).

### 13.9 Code generation: "C with classes"

With `-c` or `--emit-gir` in C++ mode, `cg_on` makes the semantic actions
build C's AST for C++ constructs, which the C lowering then compiles
unchanged; `cg_finish` completes the translation unit after parsing.

| C++ | as C |
|---|---|
| member function | a C function whose first parameter is `this` (`abi_type`); a call passes the object's address, adjusted to the base subobject that declares the function |
| virtual call | `((F **)*(void ***)this)[slot](this, ...)`; vtables are internal arrays of `void *` (offset to top, typeinfo, slots in Itanium order: the primary base's slots, overriders in place, new functions, complete and deleting destructors) |
| typeinfo | `__class_type_info` / `__si_class_type_info` / `__vmi_class_type_info` objects pointing to libstdc++'s vtables, with `_ZTS` names |
| reference | a pointer: variables, parameters, members and results of reference type are rewritten in `cg_finish` (`NF_REFDEREF` nodes become dereferences) |
| constructor | the object is declared without initializer, then the constructor is called on its address; a constructor's body starts with the base constructors, the vtable pointer store, the members' mem-initializers or default member initializers |
| destructor | C's `cleanup` attribute on the variable (so returns, breaks and gotos run it); a destructor's body ends with the members' and bases' destructors in reverse |
| implicit special members | synthesized when used (default constructor, destructor, deleting destructor); copies of trivially copyable classes are struct copies |
| arrays of objects | construction loops; an array destructor function as the cleanup |
| global objects | `_GLOBAL__sub_I_<file>` (and `_GLOBAL__I_<prio>` for `init_priority`) in `.init_array`, registering destructors with `__cxa_atexit`; dynamic initialization of other globals there too |
| static locals | a guard variable (single-threaded) |
| `new`/`delete` | statement expressions calling `operator new`/`operator delete` (the deleting destructor through the vtable for a virtual destructor) |
| operators | overloaded operators, conversion functions and converting constructors resolve to calls of the chosen function |
| member pointers | a data member pointer is the member's offset (null: -1); a member function pointer is Itanium's `{ ptr, adj }` (a virtual function: `1 + 8 * slot`), called through a test of `ptr & 1` |
| names | Itanium mangled names as asm labels; inline functions (defined in their class, `inline`, implicit) are internal and emitted on use |

The C lowering needed one change, effective in C++ only so that C objects
stay identical: a `goto` forward out of the scope of an object with a
destructor jumps to a block filled at the label, which runs the
destructors between the two scopes (C's own lowering does not run
`cleanup` functions for forward gotos; for C this remains as it was).

`cg_finish` then walks the code the C lowering will emit, starting from
the external definitions and following references: it rewrites
references, base class conversions (`CK_DERIVED2BASE`) and C++ lvalue
conditionals into C, lowers the types, and reports the first construct D1
does not lower (an opaque node, a C++ node kind, a C++ type left) as
`goosecc: C++ code generation (D1) does not support ... yet` with its
location; nothing is emitted then. Unused inline functions in headers are
never walked, so a header full of templates does not stop a program that
does not use them.

Not lowered in D1: templates (no instantiation), exceptions (`throw`,
`try`), temporaries with non-trivial destructors (and so passing or
returning such classes by value), member pointer conversions to
bases at a non-zero offset and comparisons, `typeid` and
`dynamic_cast`, lambdas, range-based `for`, virtual and multiple
polymorphic bases, implicit copy constructors and assignment operators of
classes that are not trivially copyable, class-specific `operator
new`/`delete`, argument-dependent lookup beyond the operands' namespaces.

### 13.10 Roadmap

- **D2: templates.** Instantiate class templates and function templates
  by re-parsing their token ranges with the arguments bound (the
  machinery of 13.4: `subst_parse`, `vis_limit`), with template argument
  deduction, partial ordering, SFINAE in deduction, and the lazy
  instantiation of members; argument-dependent lookup. Target:
  `std::vector`, `std::string`, iostreams compile; the declaration
  oracle's 171 missing declarations (all in templates) appear.
- **D3: the rest of the lowering.** Temporaries and their destruction at
  the end of full-expressions (including conditional ones), classes passed
  and returned by invisible reference, implicit copy/move operations,
  lambdas, range-based `for`, RTTI (`typeid`,
  `dynamic_cast`), multiple and virtual inheritance (thunks, VTTs,
  construction vtables), and then exceptions (`.eh_frame`/LSDA tables from
  the C lowering, which the Goose back-end already emits for `goovm-llc`).
  Target: the SingleSource C++ tests and the CTMark C++ programs.
- **D4: C++20.** Concepts and `requires` (the cxx-hdrs files under
  `-std=gnu++20`), `consteval`, `<=>` rewriting, designated initializers;
  then modules are out of scope.
- **Speed.** Header-heavy C++ is dominated by preprocessing and parsing
  the standard library: the B4 header cache applies as is; the G1 parse
  cache (C's parser state) would need the C++ side tables (`cxs`, `crecs`,
  `nmap`, scopes, templates) in its snapshot.
