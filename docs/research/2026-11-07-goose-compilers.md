# goovm：Goose で作ったコンパイラの実装結果

報告日: 2026-11-07。[2026-11-06 の検証結果](2026-11-06-results.md)を受けて、「Goose で本格的に作る」方針で実施した開発（A1〜A5、B1〜B5）をまとめる。

数値はすべて、この環境（4コアの VM、clang/LLVM 20.1.2）での [実測] である。最終計測は他の作業を止めて行った（負荷平均およそ1）。

---

## 0. 結論

**Goose で、C と C++ の `-O0` コンパイラの部品を実装した。どれも clang と同じ正しさで動く。**

| 成果物 | 中身 | 規模 |
|---|---|---|
| **Goose 製バックエンド** (`backend-goose/`) | 次をすべて扱う。clang `-O0` が C/C++ から出す LLVM IR、レジスタ割り当て、DWARF 5、`.eh_frame`、C++ の例外、comdat | Goose 約9,700行 |
| **`goovm-cc`** (`tools/goovm-cc/`) | clang のフロントエンドを同じプロセス内で動かし、IR を Goose 製バックエンドへ直接渡す。`clang -c` の代わりにそのまま使える | C++ 約5,300行（LLVM IR から GIR への変換と DWARF の構築を含む） |
| **`goosecc`** (`frontend-goose/`) | LLVM を一切使わない C コンパイラ。前処理・構文解析・型検査・GIR 生成を Goose で書き、同じプロセスで Goose 製バックエンドを呼ぶ | Goose 約23,000行（手書き。B5 の DWARF を含む）＋約6,100行（生成） |

**正しさ：** 次の5つが、どれも clang と同じ結果になった。

- `goovm-llc` と `goovm-cc` で、C/C++ のテスト1,915本を5通りの変種（`-O0`、`-g`、mem2reg、`goovm-cc`、`goovm-cc -g`）で実行し、全部通った。LLVM への逃げ道は0回。
- `goosecc` で、C のテスト1,804本を `-O0` と `-g` で実行し、全部通った。
- CTMark の全10プログラム（C 6本、C++ 4本）が、公式の期待出力を出した。
- `-g` を付けたオブジェクトは、すべて `llvm-dwarfdump --verify` を通った。
- `goosecc -g` の DWARF（変数・型・スコープまで）は、両方がコンパイルできる2,288ファイルのうち2,231本で clang `-O0 -g` と同一になった（B5、§2.2）。

**速さ（CTMark 全632ファイル、`-O0`、全段階を統合した最終版での再計測。§3.1）：**

| 比較 | 速さ |
|---|---|
| `goosecc` 対 clang（C ファイル316本） | **8.9倍速い**（13.37秒 → 1.50秒、ヘッダキャッシュあり）。キャッシュなしでは7.9倍（1.69秒） |
| `goosecc` 対 TinyCC（同じ316本） | キャッシュありで1.06倍速い（1.50秒 対 1.59秒）。キャッシュなしでは TinyCC が1.06倍速い |
| `goovm-cc` 対 clang（全632本） | 1.07倍速い（`-g` 付きは1.12倍）。C++ はフロントエンドが大半を占めるため小さい。sqlite3 では1.55倍 |
| バックエンド単体 | LLVM `-O0` の13〜27倍速い。LLVM IR からの変換を含めても TPDE と同等か、それより速い |
| 出力コードの質 | CTMark の全10本で clang `-O0` と同等（0.95〜1.02倍、幾何平均0.98倍）。浮動小数点の多い C++ も、C1 で追いついた（Bullet 1.73倍→0.97倍、tramp3d-v4 1.22倍→1.02倍）。`.text` の大きさは llc の1.00〜1.07倍 |

**何が効いたか：**

- 速さの大部分は**設計**から来ている。一発で生成すること、IR を平坦な表で持つこと、ヘッダを毎回読み直さない工夫などである。
- **Goose のメモリモデル**（伸ばしても動かず、容量の確認もない配列）も、素直に書いた C++ の約2倍の速さに効いた。ただし C++ を手で調整すれば、差は約1.2倍まで縮む。

**限界：**

- **C++ のフロントエンドは clang のまま。** C++ のビルド全体は約1.1倍しか速くならない。C++ の時間の大半は clang のフロントエンドが占めるためである。
- **最適化は `-O1` 相当まで（E1、§7）。** 出力コードは CTMark で clang `-O1` の1.57倍の時間（抽象化の多い C++ と浮動小数点の多いコードで差が大きい）。
- **対応環境は x86-64 Linux だけ。**
- **`goosecc` の DWARF は、clang と違うコードを出す箇所では clang と一致しない。** B5 で変数・型・スコープまで clang `-O0 -g` と同じものを出すようになったが、clang が畳み込む const 変数や `-O0` でもインライン展開する `always_inline` 関数など、生成コード自体が違う箇所の DIE は違う（§2.2）。

## 1. 構成

```
                ┌───────── goovm-cc（clang -c の代わり）─────────┐
C/C++ ── clang フロントエンド（プロセス内）── LLVM IR ── 変換器（C++）──┐
                                                                         ├─ GIR v2 ─ Goose 製バックエンド ─ ELF .o
C ──── goosecc：前処理 → 構文解析・型検査 → GIR 生成（すべて Goose）──────┘   （レジスタ割り当て、DWARF、
                                                                            .eh_frame、C++ 例外表）
```

- **GIR v2**（`gir/gir.h`）
  - パディングのない固定長レコードの表で、C++ からも Goose からも、コピーせずにそのまま読める。
  - 型表、24バイトの命令、ABI 情報、セクション、TLS、comdat、例外表、DWARF の DIE などを持つ。
  - 変更はすべて追加の形で行い、既存の形式は保った。
- **開発の順序**

| 段階 | 内容 |
|---|---|
| A1 | IR を全部扱えるようにする |
| A2 | レジスタ割り当て |
| A3/A5 | DWARF、CFI、C++ |
| A4 | `goovm-cc` |
| B1 | 前処理・構文解析・型検査 |
| B2 | GIR の生成 |
| B3 | 高速化 |
| B4 | ヘッダキャッシュ |

  段階ごとにエージェントが独立した作業ツリーで実装し、私がビルドとテストをやり直して検証してから統合した。

### 3.3 出力コードの質

CTMark の各プログラムを、clang `-O0` と goovm でビルドして実行時間を比べた（3回のうちの最良値、シングルスレッド）。O0 は clang `-emit-llvm` と `goovm-llc` を通したもの、cc は `goovm-cc` でビルドしたもの。「C1 前」は A3 の終わりのバックエンド（コミット c96510d）を、同じ時間帯に計り直したもの。

| プログラム | clang `-O0` | goovm（O0） | 比 | goovm-cc | 比 | C1 前の比（O0） |
|---|---:|---:|---:|---:|---:|---:|
| sqlite3 | 3.651 s | 3.698 s | 1.01 | 3.676 s | 1.01 | 1.03 |
| SPASS | 13.414 s | 13.324 s | 0.99 | 13.289 s | 0.99 | 1.03 |
| ClamAV | 0.164 s | 0.163 s | 0.99 | 0.161 s | 0.98 | 0.97 |
| lencod | 9.275 s | 9.112 s | 0.98 | 9.136 s | 0.98 | 1.01 |
| mafft | 32.351 s | 31.308 s | 0.97 | 31.113 s | 0.96 | 0.96 |
| consumer-typeset | 0.134 s | 0.128 s | 0.95 | 0.128 s | 0.95 | 0.94 |
| 7zip（C++） | 12.296 s | 11.751 s | 0.96 | 11.900 s | 0.97 | 0.98 |
| Bullet（C++） | 16.587 s | 16.071 s | **0.97** | 16.119 s | **0.97** | 1.69 |
| kimwitu++（C++） | 0.024 s | 0.023 s | 0.95 | 0.022 s | 0.92 | 0.98 |
| tramp3d-v4（C++） | 16.949 s | 17.327 s | **1.02** | 17.178 s | **1.01** | 1.19 |
| 幾何平均（clang が50 ms 以上のもの） | | | 0.983 | | 0.981 | 1.070 |

- **マイルストーン C1 で、浮動小数点の多い C++ も clang `-O0` と同等になった。** Bullet は1.69倍から0.97倍、tramp3d-v4 は1.19倍から1.02倍。ほかの8本は0.95〜1.01倍で、C1 前との差は±0.04以内（計測の揺れと同じ程度）。
- **原因は浮動小数点の演算そのものではなかった。** 加減乗除、比較、変換の命令列は、もともと LLVM の FastISel と同等だった。原因は次のとおり（詳細は `backend-goose/NOTES.md` §11）。
  - Bullet：4つの float からなる `btVector3` を返す関数の戻り値（`{<2 x float>, <2 x float>}`）を、4バイトずつメモリへ書いてから8バイトで読み直していた。読み込みがストアからの転送に失敗し、1回につき約15サイクル待つ。差の76%がこれで、残りもその戻り値のメモリ経由のコピーだった。
  - tramp3d-v4：関数の出口の `leave` 命令。このホスト（Sapphire Rapids）では、小さな関数の呼び出しが連なると、1回の戻りごとに約5サイクル余分にかかる。LLVM と同じ `add rsp, n; pop rbp` に替えた。
- **SingleSource の浮動小数点ベンチマークも速くなった。** 141本を流して、遅いものを調べた。
  - `cvtsi2sd` などが、書き込み先のレジスタの前の値を待つ「偽の依存」があった。書き込み先をゼロにしてから変換する。spectral-norm は1.64倍から0.53倍、fp-convert は1.51倍から0.75倍、flops-4〜8 は0.17〜0.26倍になった。clang `-O0` のコードもこの依存を持つが、たまたま別のレジスタを使って避けている場合がある。
  - 配列の要素 `a[i]` で、ポインタの読み込みを添字の読み込みの後ろへ遅らせていたため、Linpack が1.13倍遅かった。プログラムの順に読むようにして0.99倍になった。
- tramp3d-v4 に残る差は、コードの置き場所によるもの。最も時間のかかる関数は clang の出力と1バイトも違わず、アドレスだけが違う。clang 自身のビルドも、関数の境界を64バイトにそろえるだけで0.944倍に変わる。計り直すたびに1.01〜1.07倍のあいだで揺れた。
- 生データは `bench/results/c1-2026-11-07/`（C1 前の計測は `bench/results/final-2026-11-07/runtime-ctmark.md` にもある。そのときは Bullet 1.73倍、tramp3d-v4 1.22倍）。

### 3.4 C++ と Goose の差の要因（同じ設計どうしの比較。バックエンド v0 で検証）

- Goose 版は、素直に書いた C++ 版より2.1〜2.4倍速かった。
- C++ に同じメモリの使い方（予約したアドレス空間を伸ばしていくバッファ、容量の確認なし、事前確保、インライン化）を入れると、差は1.16〜1.26倍まで縮んだ。
- 結論として、Goose の価値は「速い書き方が標準になる」ことにあり、言語そのものが魔法のように速いわけではない。詳細は [2026-11-06-results.md](2026-11-06-results.md) §4.5。

### 3.5 `goosecc` のヘッダキャッシュ（B4）

B4 で、`goosecc` に前処理の結果を残す永続キャッシュを入れた。PCH に近いが、利用者は何も指定しなくてよい。設計と正しさの根拠は `frontend-goose/DESIGN.md` §10、使い方と数値は `frontend-goose/README.md` にある。

- **単位：** `#include` 1つ。探索、ファイルの読み込み、その中の `#include` までを含む。
- **記録：** 単位の前処理が状態に与えた効果を残す。トークン、定義したマクロ、読んだファイル、ガードや `#pragma once` の状態、`__COUNTER__` などである。あわせて、単位が読んだ外の状態を残す。マクロの定義の有無と中身、ファイルの同一性（stat）、探索で見つからなかったパスである。
- **再生：** 次のコンパイルで、読んだ状態が同じことを確かめてから、効果を各配列の末尾に付け足す。再生後の状態は、前処理した場合とバイト単位で同じになる。このため出力は、キャッシュが空でも、温まっていても、無効でも同一である。
- **保存先：** `$GOOSECC_CACHE` か `~/.cache/goosecc`。一時ファイルと rename、追記で書くので、並行するコンパイルや壊れたファイルにも耐える。大きさの上限（既定2 GB）を超えると、使われていないものから消す。

## 4. Goose で書いて分かったこと

各段階の `NOTES.md` から要約する。実際のエラーメッセージは、各 `NOTES.md` にそのまま載せてある。

**良かった点**

- 大きなコードでも、一発で型検査を通ることが多かった。v0 の移植1,087行、変更可能なグラフの試作、B2 の GIR 生成がそうだった。
- 境界チェックが、変換器とバックエンドの食い違いを、ファイル名と行番号付きの異常終了として捕まえた。
- `checkfree fn` で、エンコーダ全体に境界チェックが残っていないことをコンパイラに保証させられた。
- データスタック上の配列は、追加が「書き込み＋ポインタを進める」だけで済む。速いコードが標準の書き方で出てくる。

**苦労した点**

- **再帰の規則：** 再帰呼び出しをまたいで、伸びる配列を持ち越せない。C フロントエンドでは94関数が `recursive fn` になり、作業用の配列はグローバル変数を使ったスタックで管理するしかなかった。
- **予約語との衝突：** `pad`、`type`、`block`、`guard`、`loop`、`in` が名前に使えず、エラーメッセージもそれが予約語だと教えてくれない。
- **型変換の多さ：** 変換が数百箇所に及び、そのうえ「冗長な変換」という警告も数百件出た。黙って誤る式もある。u32 のシフトの切り詰めや、u32 の引き算の折り返しである。
- **境界チェック解析の取りこぼし：** 解析が予算切れでアサーションを無視する。安全と分かっているチェックを外す手段もない。
- **見えないコスト：**
  - 参照で受け取った配列への push は、1要素ごとにカウンタ2つをメモリへ書き戻す。
  - グローバル変数の配列1つごとにデータスタックを1つ確保するため、起動時に100以上の領域を作ることになった。
- **仕様の穴の可能性：** `export fn` が受け取ったスライスをグローバル変数に保存でき、呼び出しの後に、解放済みのメモリを指したまま残りうる。
- **評価順序（B4）：** `w[f()]` で `f` が `w` に追加すると、長さは添字の評価前に読まれるので、境界チェックが古い長さで失敗する。
- **`extern fn` を越えられないスライス（B4）：** mmap した領域をスライスとして返せない。1語ずつ読む関数を C で書き、境界チェックも手で書いた。

- **木を作る再帰（B5）：** DIE の構築は本質的に再帰で、`recursive fn` が13個増えた。再帰をまたいで配列を持ち越せない規則のため、型の部品はグローバル変数のスタックに積んだ。スコープの木をたどる処理は明示的なスタックで書き直したが、その版に唯一の無限ループのバグが入った。
- **型変換の優先順位（B5）：** `x as i64 & FLAG` が構文エラーになり、範囲 `a as i64..b as i64` は「variable mode (..) applies only to ADT type names」という的外れなメッセージになる。

Goose の作者への改善提案（領域の一括予約、clz を使った実行時の除算、`extern fn` の複数戻り値、境界のずれた u64 の読み込みなど）は、`frontend-goose/NOTES.md` §10 にある。B4 で分かったことは同じく §11、B5 は §12 にある。

## 7. マイルストーン E1：最適化モード（`-O1`）

追記日: 2026-11-08。§5 の候補5「最適化パスの Goose 化」を実施した。GIR の見出しに最適化レベルを足し（`opt_level`、追加のみ）、それが1以上のとき、Goose 製バックエンドは自前の中間層で表を最適化してから、大域レジスタ割り当てつきでコードを生成する。`-O0` の経路は変えていない（§7.2）。

### 7.1 作ったもの

- **中間層**（`backend-goose/opt*.goose`、Goose 5,304行）：関数ごとに GIR の命令表を作業用の平坦な配列（OIR）に読み込み、最適化して新しい表に書き出す。使用リストやハッシュ表を常に保つことはせず、必要なパスがその場で CSR 配列を作る。関数は呼ばれる側から順に処理し、インライン展開は最適化済みの本体を写す。パスは次のとおり。
  - CFG・支配木・支配辺境・自然ループ。mem2reg（生存で刈ったφ配置）、SROA（定数オフセットのスライス、memcpy/memset の分割）。
  - 命令の単純化（定数畳み込み、恒等式、2の冪と定数での除算の書き換え、比較・キャスト・GEP、`pow(x, 2.0)` → `x*x`）。
  - 支配木に沿った CSE と、ロードの転送（逃げない alloca は別の世代で追う）、ブロック内の不要ストア削除。
  - SimplifyCFG（定数分岐、ブロックの併合、空ブロックの飛び越し、φ上の分岐のジャンプスレッディング、小さな三角形・菱形の select（cmov）化）。
  - インライン展開（大きさで判断：40命令まで、ループ内は80、1か所からしか呼ばれない内部関数は500）、末尾再帰の除去（累積値つき）。
  - ループ回転（先頭の判定を入口に複製して do-while にする）、LICM（GEP の分割を含む）、帰納変数の i64 化、アドレスを取られない内部大域変数のループ内でのレジスタ化、DCE、配置でのループ回転。
  - `GOOVM_OPT=verify` で、最適化後の SSA と CFG の不変条件（オペランドが使用を支配する、φの入口が前任と一致する、など）を関数ごとに確かめる。
- **大域レジスタ割り当て**（`backend-goose/rag.goose`、859行）：ブロックをまたぐ値とすべてのφに、生存範囲全体で1つのレジスタを与える（与えられなければ `-O0` と同じくスタック上の置き場所に書き通す）。生存はビット集合の後ろ向きデータフロー、範囲は命令位置の区間、呼び出しが壊すレジスタを避け、ループの深さで重みを付けて順に割り当てる。φの入力は辺ごとの並列コピー。ブロック内の割り当て器（A2）は、固定された値を避けて動き、足りないときは使わない固定値のレジスタを1命令だけ借りる。callee-saved レジスタも使う。CFI は正確なまま。
- **配線**：`goovm-llc -O1`（clang `-O0` の IR）、`goovm-cc -O1`（clang のフロントエンドを `-O0` の意味で、ただし optnone なしで動かす）、`goosecc -O1`（`frontend-goose/src/main.goose` に1行）。GIR の追加はすべて後方互換（`opt_level`、`FN_NOINLINE`/`FN_ALWAYSINLINE`、`IF_NSW`、データ再配置 `PCREL32`）。

`tests/suite.py` の全11コーパス（1,921本。clang `-O0` で通る1,915本のうち、clang `-O1` でも通る1,894本が最適化の変種の対象）。`GOOVM_OPT=verify` と `--verify-dwarf` 付き。

### 7.5 LLVM `-O2` の IR を Goose のバックエンドで

clang `-O2 -fno-vectorize -fno-slp-vectorize` の IR を `goovm-llc -O1` に通すと、CTMark 8本の幾何平均で clang `-O1` の **1.19倍**（表の右端の列）。Bullet は3.34倍から1.20倍に、tramp3d-v4 は3.06倍から1.10倍になる。差の大部分は中間層にあることになる（C++ の小さなメソッドを LLVM はインライン展開してから SROA で分解するが、Goose の中間層は大きさの上限と SROA の制約で呼び出しとコピーを残す）。逆に mafft（1.76倍と1.78倍）と sqlite3 の一部はバックエンドの差で、mafft の2つの動的計画法のループ（実行時間の98%）は、ループ不変の浮動小数点値をフレームに置いたままにする。関数内の別の場所で呼び出しをまたいで生きる値は、callee-saved の xmm レジスタがなく、生存範囲の分割もしないので、どこでもレジスタを得られない（LLVM の greedy 割り当ては呼び出しの周りで分割する）。

エクスポータは E1 で、飽和加減算、相対参照のルックアップ表（`PCREL32`）、`llvm.load.relative`、`fastcc` を受け付けるようになった。残る非対応（`-O2` の IR、ファイル単位）：全2,651ファイル中165ファイルで、ほぼすべてベクトル化の出力である（ポインタのベクトル72、`llvm.vector.reduce.*` 61、ベクトルと整数のビットキャスト22、その他10）。ベクトル化を止めると（`-fno-vectorize -fno-slp-vectorize`）7ファイルになる。詳細は `backend-goose/NOTES.md` の12節。

### 7.6 残る差と次の手

1. **生存範囲の分割**（呼び出しの周りで浮動小数点値を退避する）：mafft、Bullet、浮動小数点の多いコード全般。
2. **インライン展開と SROA の強化**：引数を介した集約の分解、sret の戻り値、費用の見積もり（引数が alloca や定数のときの割引）。Bullet と tramp3d-v4 の差の大部分。
3. 条件付きでしか書かれない大域変数のレジスタ化（フラグつきの書き戻し）、ループの展開、`noinline` の情報を GIR に残す方法（`-O0` の IR では失われる）。

### 7.7 Goose で書いて分かったこと（E1）

- **大域の構造体が見ている配列は縮められない**：中間層の出力表を `M` に向けると、次のモジュールのために `clear` することを「`global M may hold a reference into it`」として拒む。正しい規則だが、「`M` は読む前に付け替える」と言う方法がない。出力表は追記だけにし、呼び出しごとの領域の先頭（`xb_*`）を持った。
- **構造体を丸ごと代入すると、解析が同じ型の配列すべてに広がる**：`M = Module { ... }` とすると、`vi` や `b_tag` のような無関係な配列の `resize` まで拒まれた。フィールドごとに代入すると正確なまま。
- **同じコードが、組み込む先のプログラムで別の判定になる**：goosecc に組み込むと、goovm-llc では通ったコードが「`cannot resize vi while blocks is still used ... read out of M`」で拒まれた（上と同じ対処で解決）。
- **大域名の名前空間が1つ**：`sc_epoch` が `dwarf.goose` と衝突した。中間層の大域変数にはすべてパスの接頭辞を付けた。
- **型のない整数定数は、推論される場所で `i64` になる**：`F(0)` を呼ぶ総称関数に渡したブロックの引数が `i64` になり、`cannot pass i64 as u32` になる。定数に型を付けて回避した。
- **文字列の表は型を付けると添字で引けない**（`arrays of variable-size elements cannot be indexed, only iterated`）。型のないリテラルなら引ける。
- **ブロック式は `||` のオペランドにならない**。
- **`%` はユークリッド剰余**：C の `srem` を畳み込むときに間違え、gcc-c-torture の `bitfld-1` で見つかった。
