# Goose による LLVM 高速化 — 初期調査報告

調査日: 2026-11-05

根拠の種類は次の記号で示す。

- **[実測]**: この環境で測った値
- **[原文]**: リポジトリや一次資料の原文で確認した内容
- **[S]**: 検索結果の抜粋のみで、本文は未確認

---

## 0. 結論

1. **LLVM を Goose へ全面移植するのは、現時点では成立しない。**
   - LLVM は llvm/ 以下だけで約355万行ある（C++。TableGen 定義の .td がさらに71万行）。
   - LLVM の設計は関数ポインタ・仮想関数・プラグイン・分割コンパイルに依存している。Goose はこのどれも持たない。
   - Goose の処理系は公開から約2週間で、実際にコンパイルされた最大のプログラムは3,318行。
2. **速さは言語ではなく設計から来る。** 先行事例はこの点で一致している。
   - TPDE（C++）は LLVM（C++）より10〜20倍速い。言語は同じで、設計だけが違う。
   - mold は C++ から Rust に書き直しても速度が変わらなかった。
   - Go は C から Go への機械的な翻訳で、ビルドが約2倍遅くなった。
   - Goose の出力は C なので、Goose で書けるデータ配置は C/C++ でも書ける。Goose の利点は、それを安全に書けることにある。
3. **Goose を C++ から呼ぶ局所的な置き換えは可能。ただし効くのは「粗い粒度」の場合だけ。**
   - 個別パス（InstCombine など）を置き換えると、往復の変換コストで利得が消える。
   - 有望なのは `-O0` のバックエンドを丸ごと置き換える案（IR → .o）。ただしこの設計は TPDE がすでに C++ で実現しており、比較相手は TPDE になる。
4. **「コンパイル速度」がどの場面を指すかで、打つべき手が変わる**（§1）。最初にこれを決める必要がある。

---

## 1. 前提の整理：「コンパイル速度」は少なくとも3種類ある

| 場面 | 時間の大半を占めるもの | 効く手段 |
|---|---|---|
| (a) デバッグビルド（`-O0`） | C/C++ ではフロントエンドが半分以上。LLVM のバックエンドは15〜42% | 一発生成型のバックエンド（TPDE や Zig 型） |
| (b) リリースビルド（`-O2`） | LLVM の最適化とコード生成が約94% | パスの削減・改良（地道な調整） |
| (c) LLVM 自身のビルド | C++ フロントエンドが79%（ヘッダの解析だけで55%） | PCH、unity build、ccache、dylib |

(c) を Goose で改善することはできない。全体プログラムコンパイルで C ファイルを1つしか出さないため、むしろ悪化する見込みが高い（§6）。

## 2. Goose の概要 [原文]

- **素性：** 作者は Wouter van Oortmerssen 氏（Lobster の作者）。ライセンスは Apache-2.0。2026年10月末に公開された。処理系は約3万行の C++（README の記載。実際に数えると約6.7万行）で、大半を AI（Claude Fable）が書いた。
- **メモリモデル：** ヒープも GC も参照カウントもない。メモリは、コンパイラが静的に割り当てる「データスタック」（バンプポインタ）だけ。
- **主な制約：**
  - 構造体が持てる可変長データは末尾の1つまで。可変長の値は配列の要素にできない（spec:474, 490）。
  - 関数値は保存できず、関数ポインタも vtable もない。動的な振り分けは ADT のタグによるものだけ（spec:2849）。
  - 全体プログラムコンパイルのみで、分割コンパイルも共有ライブラリもない（tutorial:1628, spec:4127）。
  - 再帰呼び出しをまたいで可変長データを持てない（spec:2987）。
  - スレッドは、メモリを共有しない別プログラムとして動く。やり取りできるのは平坦な値だけ（spec:4485）。
- **出力：** C ファイル1つ。同梱の TinyCC で即時実行するか、外部の C コンパイラでビルドする。
- **成熟度：**
  - 仕様は「v4 draft」。
  - 直近60コミットのうち約30件が、寿命解析の漏れの修正（analysis_inventory.md:40）。
  - Goose で書かれたコンパイラ（test/goose_in_goose）は3,321行の部分実装で、テスト用の資材という位置づけ。
- **規模に関する既知の問題 [S]：**
  - issue #226：呼び出しの入れ子が深くなるたびに、検査時間が倍になる。
  - issue #227：生成される C の入れ子が深すぎて、clang が受け付けない場合がある。
  - https://github.com/aardappel/goose/issues/226, /227
- **自己申告の実行速度：** 16本のベンチマークの幾何平均で、熟練者の C++ の約1.24倍。ミュータブルなグラフ操作に近い `lru` では、MSVC で負けている（bench/summary.md）。

## 4. LLVM はどこで時間を使っているか

### 4.1 計測方法 [実測]

- 対象：CTMark の sqlite3（84,545行の単一 C ファイル）。CTMark は llvm-test-suite に含まれる、コンパイル時間計測用の10プログラム（計約74万行）。
- 環境：clang 18.1.3、4コア。`-ftime-trace` で計測。

### 4.2 段階別の内訳 [実測]

| | 合計 | フロントエンド | 最適化 | コード生成 |
|---|---:|---:|---:|---:|
| `-O0` | 0.63s | 0.35s（56%） | ほぼ0 | 0.26s（42%） |
| `-O2` | 9.64s | 0.54s（6%） | 4.98s（52%） | 4.12s（43%） |

時間のかかっていた処理です。

- `-O2` の最適化：InstCombine 0.98s、GVN 0.53s、Inliner 0.45s、SimplifyCFG 0.31s。突出した1か所はなく、多数のパスに分散している。
- `-O2` のコード生成：SelectionDAG による命令選択が約1.5s、Greedy レジスタ割り当てが0.43s。
- `-O0` のコード生成：アセンブリ出力とオブジェクト生成が0.18s、命令選択が0.11s。

### 4.3 IR を別の形式に変換するコスト [実測]

sqlite3 の `-O0` の IR（約11万命令、概算）を使った。

| 処理 | 時間 |
|---|---:|
| ビットコードを読み込む | 118 ms |
| 全命令を1周する（verifier） | +16 ms |
| ビットコードを書き出す | +98 ms |
| `llc -O0`（IR → .o） | 532 ms |
| `llc -O2` | 999 ms |

IR を1回平坦化するコストは、バックエンド全体の数%にとどまる。一方、LLVM の IR を作り直すコストはビットコードの読み込みと同程度（約100ms）かかる。

### 4.4 文献から

- SPEC を clang `-O0` でコンパイルすると、LLVM のバックエンドは全体の約15%。TPDE を使うと2%に下がるが、全体の速度向上は17%にとどまる [S]。 https://arxiv.org/pdf/2505.22610
- libLLVM.so のビルドでは、CPU 時間の79%がフロントエンド（ヘッダの解析55%、テンプレートの実体化19%）[原文]。 https://github.com/llvm/llvm-project/pull/173868
- Rust（TiKV）では、LLVM がリリースビルドの84%、デバッグビルドの35%を占める [S]。 https://www.pingcap.com/blog/reasons-rust-compiles-slowly
- nikic（2026年1月）：LLVM は「速くなったのではなく、遅さがましになっただけ」で、`-O0` が特に悪い [S]。 https://www.npopov.com/2026/01/11/LLVM-The-bad-parts.html
- Engelke：問題の根は、ポインタをたどるアクセス、use-def リスト、IR を少しずつ書き換える設計にある。LLVM の根本的な性能は「すぐには変わらない」[S]。 https://llvm.org/devmtg/2025-04/slides/technical_talk/engelke_faster.pdf

## 5. 先行事例：速さは言語ではなく設計から来る

| 事例 | 言語 | 中心となる考え方 | 速さ | 代償 |
|---|---|---|---|---|
| TPDE-LLVM [原文] | C++ | 解析と、命令選択・レジスタ割り当て・符号化を融合した1回の走査 | LLVM `-O0` の10〜20倍 | コード品質は `-O0` と同等。x86-64 と AArch64 の ELF のみ |
| Zig 独自 x86_64 [S] | Zig | LLVM を使わない独自バックエンド | 壁時計時間で5〜50%減 | 生成コードは弱い |
| Cranelift [S] | Rust | Wasm 向けのコード生成器 | LLVM `-O0` 比で20〜35%速いだけ | 実行速度は約14%遅い |
| MIR [原文] | C | 短いパイプライン | gcc `-O2` の109倍（1本のベンチ） | 実行速度は gcc `-O2` の91% |
| V8 Turboshaft [S] | C++ | sea of nodes をやめ、制御フローグラフで持つ | コンパイル時間が半減 | 品質の低下なし |
| mold 3.0 [原文] | C++ → Rust | 言語だけを変えた | 2.42（C++ 版）と同等 | なし |
| Go 1.5 [S] | C → Go | 機械的な翻訳 | ビルドが約2倍遅くなった | — |

言語を変えて速くなった例はなく、速くなった例はどれも設計を変えている。

## 6. Goose で LLVM を書き直す場合の適合性 [原文 + 推論]

| LLVM の部品 | 評価 | 理由 |
|---|---|---|
| IR の中核と use-list | 工夫すれば可 | slot_pool の上に、プール内の侵入型リストを置く。古いハンドルは検出できない |
| 解析・最適化パス | 工夫すれば可 | 辞書は固定長要素のみ。関数ごとに可変長コンテナを持てない |
| パスマネージャ | 工夫すれば可（プラグインは不可） | enum と match で書く。動的なプラグインは書けない |
| 命令選択（SelectionDAG / GlobalISel） | 工夫すれば可 | グラフ変更の工夫が同じく必要 |
| レジスタ割り当て | 比較的自然 | 配列中心のデータで済む |
| MC 層とオブジェクト出力 | 工夫すれば可 | 可変長のセクションは slice_pool で持つ（伸ばすたびにコピーされる） |
| ターゲット登録（複数ターゲット） | 工夫すれば可 | 閉じた enum になり、外部ターゲットは不可 |
| 並列化と ThinLTO | 共有メモリは不可 | 平坦なデータをコピーで受け渡す方式になる |
| clang や rustc 向けの C/C++ API | 現状は不可 | 公開できるのは平坦な C 関数のみで、1スレッド限定 |
| LLVM 自身のビルド | 悪化の恐れ | 全体プログラムコンパイルで単一スレッドの検査、C の翻訳単位は1つ |

## 7. C++ から Goose を呼び、局所的に置き換える場合

### 7.1 境界で何ができるか [原文, spec §7.10–7.11]

- **組み込み方：** `export fn` と `--header` で、C ヘッダと `goose_init()` が生成される。生成された .c を LLVM のビルドに加える。
- **渡せる引数：** スカラー、平坦な固定長の値、`T&`、`T[:]`（ポインタと長さ）。
- **返せる値：** スカラーか平坦な値、または `const u8[:]` だけ。
- **制約：**
  - 呼び出せるのは初期化したスレッドからだけで、プロセス内にランタイムは1つだけ（spec:3422, 3436）。
  - Goose 側から C++ のオブジェクトはたどれない。C から Goose へのコールバックには、C 側の仲介関数が必要。

### 7.2 置き換える粒度ごとの評価（§4.3 の実測による）

| 置き換える単位 | 評価 | 理由 |
|---|---|---|
| 個別パス（InstCombine など） | ✗ | 実行のたびに IR の往復変換が必要（約100ms級）。依存する解析（ValueTracking、TTI、AA）もすべて書き直しになる |
| オブジェクト出力やレジスタ割り当ての中核 | △ | 全体に占める割合が小さいか、LLVM の機械語 IR（MIR）への依存が強い |
| `-O0` のバックエンド丸ごと（IR → .o） | ◎ | 平坦化は1回で済み、出力もバイト列1本。境界のコストはバックエンドの数% |

### 7.3 効果の見積もり

TPDE 並みの10倍速いバックエンドができると仮定する。

- sqlite3（C、`-O0`）：0.63s → 約0.40s（約1.6倍。フロントエンドが残るため上限は約1.8倍）
- SPEC 相当の C/C++：約1.17倍（文献値）
- Rust のデバッグビルド（LLVM が35%）：約1.4倍（推定）
- `-O2`：効果なし

### 7.4 必要になる独自ライブラリ

1. **C++ 側：** LLVM IR を SoA の平坦な表に書き出すエクスポータ。
2. **Goose 側：** 一発生成型のバックエンド（x86-64 の機械語と ELF を出す）。
3. **接着部分：**
   - CMake への統合。
   - スレッド制約への対策。Goose 専用スレッドを立てるか、Goose のランタイムを改造してスレッドごとに状態を持たせる（Apache-2.0 なので改造可）。
4. **検証：** CTMark でコンパイル時間を比べ、llvm-test-suite で出力コードの正しさを確かめる。

## 8. 主なリスク

1. **データモデルの不一致。** IR、MIR、DAG、解析結果のキャッシュは、インデックスで参照し合う表として作り直す必要がある。手動の解放は検査されない。
2. **Goose の処理系が大規模コードに耐えられるか不明。** 3.3k行を超える実績がなく、#226 と #227 のような規模に関わる問題がすでに出ている。
3. **段階的な移行ができない。** C への公開口が狭いため、clang や rustc などの利用者が API を失う。
4. **閉じた世界。** プラグインも外部ターゲットも書けない。参照の起点ごとの特殊化でコードが膨らむ恐れがある（未計測）。
5. **言語が若い。** 仕様は draft で、所有権や move などの主要機能は設計メモの段階。
6. **比較相手がすでにある。** TPDE が C++ で同じ設計をすでに実現している。Goose 版がそれに勝てないなら、作る理由がない。

## 9. 進め方の提案

- **Phase 0：前提を決める（数日）**
  - 対象とする場面（§1 の a / b / c）と言語（C / C++ / Rust など）を決める。
  - CTMark 全体で、最新の clang の時間内訳をベースラインとして測る。
- **Phase 1：Goose の検証（1〜2週）**（この環境で Goose をビルド・実行する許可が必要）
  - `export fn` を C++ から呼ぶ最小構成を作り、呼び出しのオーバーヘッドを測る。
  - 平坦な IR を1周する処理を Goose と C++ で書き、速度を比べる。
  - 合成した大規模プログラム（1万〜20万行）で、Goose コンパイラ自体がどう伸びるかを測る。
- **Phase 2：バックエンドの試作（数か月）**
  - 対象は x86-64 の整数演算のサブセットから始める。
  - LLVM `-O0` と TPDE の両方と比べる。
  - 続行の条件の例：Goose 版のコンパイル速度が TPDE の0.8倍以上で、安全性か保守性で明確な利点があること。満たさなければ、TPDE を採用するのが最も安くて確実。
